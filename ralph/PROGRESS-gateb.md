Warning: FVMAIN at 99% (48 bytes free): another driver does not fit without reducing something.
- **How it works:** at the driver's entry 4 EfiReservedMemoryType pages are allocated (one per CPU, BSP included, because acpigen requires a unique `parked_address` for each GICC with parking), `ProcessorId=0xFFFFFFFF`, `JumpAddress=0`, expected ProcessorId (= CPU index = `cpu_interface_number`) at +0xFF0, stub copied to +0x800, cache cleaned. At ReadyToBoot: for each core 1..3 it wakes the redistributor (`GICR_WAKER.ProcessorSleep=0`) and calls PSCI `CPU_ON` (0xC4000003, target = MPIDR = index, entry = mailbox+0x800, context_id = mailbox) through `ArmMonitorLib` (the HVC/SMC conduit is read from the DTB). The stub: enables the GICv3 CPU interface (ICC_SRE/PMR/IGRPEN1), then a WFE loop on the mailbox as per the spec; on go it zeroes JumpAddress, DSB, X0=mailbox, BR.
- **Verified sources:** QEMU virt's PSCI conduit (`hw/arm/virt.c`, lines ~2951-2955): SMC if there is EL3 (secure=on), HVC otherwise (our case `secure=off,virtualization=off`), DISABLED if neither; the secondary cores start off. Parking spec and Linux/U-Boot comparison: `re/f0-acpi-windows-requirements.md` sec. 3 (behavior rewritten by us, no code copied). 64-bit PSCI CPU_ON = 0xC4000003 (knowledge of the Arm DEN0022 spec, not re-read here).
- **[hypothesis] / uncertain points:**
  1. Modern Windows ARM64 might NO LONGER support the parking (main risk already in `re/f0`); with PSCI_COMPLIANT=0 and parking v1 the behavior is undocumented.
  2. Processor ID: we use `cpu_interface_number` (as Linux); on GICv3 without compat the spec says 0 for all: if Windows writes 0 on all, the stub does not wake up (no match on IDs 1..3). Future mitigation: also accept 0 or compare the MPIDR.
  3. Windows' wake-up is an interrupt/IPI (SGI): not necessary, the stub polls with WFE; in HVF WFE is treated almost as a NOP (busy loop on the cores, only until the OS starts).
  4. Windows starts with the cores in EL1; PSCI CPU_ON starts them in EL1 in our setup (no EL2) = state required by the spec; to be verified in the trace.
  5. Wake of the redistributors and ICC enabling done by us to respect "GIC CPU interface enabled" of Tab. 1; if Windows reconfigures them, no harm, but it is not proven that they are needed.
  6. The cores are powered on at ReadyToBoot, not at ExitBootServices: if a boot option fails and another is tried, the mailbox stays valid (`mStarted` flag).
  7. `PARKING_NCPUS = 4` is fixed: use `-smp 4`.

Who writes (hypothesis, not identified): GIC re-init code after ExitBootServices (firmware or Windows HAL); Group 1 is restored before the timer is enabled, which is why there is never a FIQ.
- **Interpretation:** experiment A INCONCLUSIVE. Method A (DXE driver at ExitBootServices) does not hold, because something puts IGROUPR0 back to 0xffffffff right after. Method B would be needed (QEMU patch to force the PPIs into Group 0 / FIQ), NOT built (requires a download: ask Marco), or identify the writer and make ours go after it. In addition the control with `kernel-irqchip=off` does not reach the lock screen, so even with B it must first be understood why.
