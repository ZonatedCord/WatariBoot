# RISKS and open questions (watari-edk2-m1)

- Project: Watari Boot, subsystem "watari-edk2-m1" · Date: 2026-11-12 · Version: 0.1 · Status: draft
- Linked documents: [README](README.md) · [DESIGN](DESIGN.md) ("D n") · [PLAN](PLAN.md) · [draft ADR](../../adr/draft-edk2-m1-platform.md)
- Probability and impact: L / M / H, the author's estimate **[hypothesis]** in every row. "Settled by" names the plan step (E1-E14) or the day-3 rung (D0-D5, PLAN H2-H7) that turns the item into a fact. Source names as in DESIGN section 0.

## 1. Risks

| ID | Risk | P | I | Why we think so | Mitigation | Settled by |
|---|---|---|---|---|---|---|
| **R-E1** | **Windows does not accept, or draws wrongly on, the panel's 30-bit `x2r10g10b10` framebuffer** | **H** | M-H (a boot without a picture cannot be diagnosed; a wrong-colour picture can) | Microsoft: `PixelFormat` "must be" 8-bit BGR [verified: MS-UEFI "Protocol requirements"]; the panel is 30-bit [verified: HW boot log]; NTASP reports 8-bit unconditionally [verified: N:…/SimpleFbDxe.c:223-229]; nothing known about Windows and `PixelBitMask` | three stages (D 8.5): truthful masks, then an 8-bit report with wrong colours, then a shadow framebuffer in the layer. EDK2 itself is unaffected (blit library handles the masks) | M3b on hardware; partly by E11 on the bench (EDK2 side only) |
| R-E2 | The guest's framebuffer mapping faults or tears: stage-2 attributes combine into Device memory, or the guest's write-combining mapping misbehaves on Apple cores | L-M | M | the combination rule is from memory [hypothesis: D 8.3]; the layer's own Normal-NC mapping of the same buffer is itself unproven until day 2 | G12 in the test guest draws with plain aligned 32-bit stores first (works under either attribute); the GOP driver's blit uses `CopyMem`, tried only after G12 passed | D1, D3 |
| R-E3 | Band arithmetic wrong on the real panel: the stride is not 4 x width, or the buffer base/size is not a multiple of 16 KB, so the band cannot end on a stage-2 page | L-M | L | stride not measured [hypothesis: D 8.1] | the layer rounds the band up to the next whole page multiple and falls back to `wel2.fb=layer` (no hand-over, with a log line) when no multiple within 128 rows exists; `gfdt_dump` shows the geometry at D0 | D0, D1 |
| R-E4 | EDK2 dies in PrePi on the M1 before its first output: the guest FDT is rejected, the image lies outside the first `/memory` range, the 64 MB UEFI region does not fit, or self-relocation fails at an address above 4 GB | M | M | PrePi's memory logic was read, not run, with RAM at `0x8_0000_0000` [verified as read: D 3.3]; the bench has RAM below 4 GB only | the hypercall console works from the first instruction, so the layer shows how far PrePi got; E6's `wel2.split` and the 128 MB rule; **bench gap: `virt` cannot place RAM above 4 GB without more than 3 GB of guest RAM** [hypothesis: `virt` RAM starts at 1 GB], so a run with `-m 6G` is added to E10 to put the image above 4 GB | E10, D2 |
| R-E5 | `ArmGicDxe` picks GICv2 on the M1 because `ID_AA64PFR0_EL1.GIC` reads 0 (TID3 emulation missing, wrong, or the local patch not applied to the tree that was built) | L-M | **H** (no interrupts: EDK2 hangs at the first timer wait) | the check exists [verified: E:ArmPkg/Drivers/ArmGicDxe/ArmGicDxe.c:22-58]; two fixes planned (D 6.1) | the build script asserts the patch is applied; the test guest's G3 proves TID3 on day 2; EDK2's `Found GIC v3` line is an expected line of D3 | E3, day 2 G3, D3 |
| R-E6 | EDK2's timer tick does not arrive on hardware although the test guest's did (different programming pattern: `CNTV_CVAL` reprogrammed in the handler, long idle `WFI`) | L | M | same virtual timer and PPI as the bench [verified: D 6.2]; the FIQ gate logic is new on hardware | the self-test counts ten ticks; the layer's per-core timer statistics on the UART | D3 |
| R-E7 | A 4 KB-granule stage 1 under a 16 KB stage 2 behaves differently on Apple cores (TLB conflict aborts, performance cliffs), or EDK2 selects something else than 4 KB | L | M-H | architecturally independent [hypothesis: D 5]; the bench runs this combination but TCG does not model TLBs faithfully; macOS itself uses 16 KB, so 4 KB is the less-travelled path on this CPU, although Linux 4 KB guests run under KVM on M1 [hypothesis: from memory] | nothing to switch in EDK2; if it fails, the layer's `wel2.gran=4k` stage 2 (supported by the CPU [verified: HW row 5]) is the first thing to try | D2-D3 |
| R-E8 | The guest FDT grows past the 32 KB gap PrePi copies it into, or PrePi's copy overwrites something | L | M | the gap is fixed by the FDF [verified: D 4.1] | E5 asserts the size bound; the FDF gap can be enlarged in our own FDF if ever needed | E5 |
| R-E9 | Including `ArmVirt.dsc.inc` drags QEMU assumptions back in (a library that touches fw_cfg, PL011 or the fixed peripheral window at run time) | M | L-M (an access to an unmapped address = stage-2 fault, reported by the layer) | the include was written for virtual machines with those devices [verified: E:ArmVirtPkg/ArmVirt.dsc.inc:135-144, 220-264] | E1/E2 check the build map for forbidden modules; any stage-2 data abort outside RAM, the vGIC windows and the framebuffer is printed by the layer with the faulting address; fall back to a flat DSC | E1-E3, E10 |
| R-E10 | A chatty firmware floods the layer: thousands of `WEL2_CONSOLE_WRITE` calls under the big lock slow the boot, or the framebuffer ticker costs too much per call | M | L | DEBUG builds print a lot; the layer's text drawing is slow by design | the ticker shows only the last line and is rate limited; RELEASE build for day 3 if needed; the UART sink is polled with a bounded wait (M1BOOT 7) | E8, E10 |
| R-E11 | The hypercall console is the only early output and it is broken on hardware (the guest-read path needs cache maintenance the bench cannot show) | L-M | M | same mechanism as `WEL2_LOG`, proven on day 2 before EDK2 runs | D2 only runs after day 2's G1 passed; the layer's "entering the guest" square and its own trap reports do not depend on the guest's cooperation | day 2, D2 |
| R-E12 | Windows expects more of the firmware than the first platform gives: persistent or authenticated variables, a real clock, a real shutdown, an RNG, SMBIOS content | M | M | Microsoft lists them as required [verified: MS-UEFI]; the bench gives QEMU's implementations, so none of the RAM-backed stand-ins has met Windows | each stand-in can be tried on the bench first by building `WatariQemuPkg` with the same stand-in (emulated variables, virtual RTC) | M3b, bench first |
| R-E13 | The minimal DSDT (processors only) is not enough for Windows, or the absence of DBG2 is fatal | M | M | Microsoft's pages name no mandatory device and do not mention processor devices [verified: D 9.2]; "Microsoft requires a debug port on all systems" [verified: MS-ACPI] | E13 on the bench with `snapshot=on`, before any hardware day; add devices one at a time | E13 |
| R-E14 | No input device: a firmware prompt or a Windows screen waits for a key forever | H (it will happen at some point) | L (for day 3), M (for M3b) | no SPI keyboard driver, no USB [verified: D 7] | boot manager library never waits; self-test ends by itself; M3b needs T15 (USB keyboard) or an unattended image | E12, T15 |
| R-E15 | Licence contamination: someone "borrows" from NTASP's Mu tree (BSD, but ADR-0007 forbids copying), from U-Boot or Linux drivers (GPL), or from the Qualcomm EDK2 ports' `SimpleFbDxe` | L | H | similar drivers exist under the same names | the plan's rules; reviewers check new files against the named upstreams; our GOP driver is modelled on EDK2's own `QemuRamfbDxe` structure only | review of each step |
| R-E16 | Day 3 depends on a chain of unproven day-2 items (TID3, both trap configurations, the FIQ timer, the framebuffer after m1n1's shutdown); a slip there moves everything here | M | M | M1BOOT RISKS R-1a..R-5 | the layer-independent parts (E1-E4, E13) are scheduled first; H1 makes day 2's success an explicit precondition | day 2 |

## 2. Open questions

| ID | Question | Current answer | Who / when |
|---|---|---|---|
| **Q-E1** | **What do the Windows boot manager and kernel do with a `PixelBitMask` GOP mode with 10-bit channels, and how bad is an 8-bit picture on the 10-bit panel?** (the riskiest open question of this design) | [hypothesis] unknown; three-stage plan in D 8.5 | M3b; H7 gives the photo for the 8-bit case |
| Q-E2 | Is the framebuffer stride 4 x width on the j293, and is the buffer a whole number of 16 KB pages? | [hypothesis] yes (10240; 1000 pages) | D0 (and already rung L0 of day 2) |
| Q-E3 | Include `ArmVirt.dsc.inc` and override, or a flat DSC? | [hypothesis] include; decided by trying | E1 |
| Q-E4 | Does Windows read `ID_AA64PFR0_EL1.GIC`? (EDK2 does: settled, D 6.1) | [hypothesis] yes; TID3 covers both | M3b |
| Q-E5 | Does the full-panel mode need the layer to stop drawing forever, or may it keep the last-resort panic screen? | decision: panic screen only (Microsoft's rule is about firmware after hand-off to a boot application; a fatal error of the layer ends the session anyway) | Marco, ADR |
| Q-E6 | Should the firmware keep a device tree for the OS (`PlatformHasAcpiDt` both)? | no: ACPI only; Windows uses ACPI, and a Linux guest is not a goal | settled here |
| Q-E7 | RAM-disk boot of Windows PE as the first Windows attempt: does the kernel need any storage driver in that mode; how long does the proxy take for a few hundred megabytes; where does the image come from (never the repository) | [hypothesis] no driver needed [verified only: Windows PE can "run … entirely from memory", MS-PE]; transfer time unknown | T14/T15 research, Marco |
| Q-E8 | Does Windows boot without DBG2/SPCR, and with a processors-only DSDT? | [hypothesis] yes | E13 |
| Q-E9 | Does the M1 implement `RNDR` (for `BaseRngLib`), and should the layer forward a seed from m1n1's `/chosen` to the guest? | not measured; [hypothesis] no `RNDR`; seed forwarding postponed because the seed is sensitive | read `ID_AA64ISAR0_EL1` on day 2 or 3 (read-only); M3b |
| Q-E10 | Where should persistent UEFI variables live once there is storage (a file on the ESP, as Asahi's world does without a variable store [verified: A:platform/open-os-interop/], or NVMe/NOR)? | open | M3b |
| Q-E11 | Should the same firmware binary serve the bench and the M1? | yes for everything FDT-driven; the bench-only PL011 switch of E3 is a separate build and is not what goes to hardware | settled here |
| Q-E12 | Is the EDK2 block's placement by the loader (`u.memalign(32 MB, 32 MB)` in m1n1's heap) always inside a guest range of at least 128 MB? | [hypothesis] yes: m1n1's heap is in the large low range; the layer refuses to chain otherwise | D0 |
