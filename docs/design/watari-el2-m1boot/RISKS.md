# RISKS and open questions (watari-el2-m1boot)

- Project: Watari Boot, subsystem "watari-el2-m1boot" · Date: 2026-11-10 · Version: 0.2 (revised 2026-11-11 after the independent review of 0.1) · Status: draft
- Linked documents: [README](README.md) · [DESIGN](DESIGN.md) · [PLAN](PLAN.md) · [draft ADR](../../adr/draft-m1-first-boot.md)
- Probability and impact: L / M / H, the author's estimate **[hypothesis]** in every row. "Settled by" names the ladder rung L0-L5 (DESIGN 9) or the plan step that turns the item into a fact.

## 1. Risks

| ID | Risk | P | I | Why we think so | Mitigation | Settled by |
|---|---|---|---|---|---|---|
| R-1a | A guest `ICC_*` access of the **`TALL0`/`TALL1`/`TDIR`** groups does not trap on the real M1 as the layer expects (wrong EC/ISS, no trap, or UNDEFINED at EL1 because `ID_AA64PFR0_EL1.GIC` = 0) | L | **H** (no unmodified GICv3 guest is possible without them: DESIGN 5.4) | KVM enables exactly these three traps on M1 cores [verified: L:arch/arm64/kvm/vgic/vgic-v3.c:616-636, 705-715]; we ourselves only proved list-register delivery [verified: HW] | guest checks G5a/G6 report each register; the EL2 sync handler prints EC/ISS of anything unexpected instead of hanging | L3 |
| R-1b | **`ICH_HCR_EL2.TC`** does not trap `ICC_PMR_EL1` / `ICC_CTLR_EL1` / `ICC_RPR_EL1` correctly on the M1 | **M** | L-M (a fallback exists) | **no precedent on this CPU**: KVM uses `TDIR` instead of `TC` here because TDS = 1 [verified: same lines]; pure [hypothesis] | `wel2.cpuif=trap-notc` (KVM's configuration), built and tested in QEMU beforehand; guest check G5b tells a `TC` failure from a `TALL1` failure; L3 runs both configurations | L3 |
| R-2 | The people see nothing: framebuffer blank or not where the FDT says after m1n1's shutdown, and no serial kit | M | **H** (a blind run teaches nothing) | m1n1 passes the same framebuffer to Linux's simplefb [verified: M:src/kboot.c:180-240]; what the panel shows after `fb_shutdown(false)` is [hypothesis] | rung L1 needs no display (the restart is the signal); checkpoint 0 is painted MMU-off right after relocation, checkpoint 1 after `s1_enable`, so a failure between them is located; the guest reports through the layer; optional serial kit | L1, L2 |
| R-3 | m1n1's `kboot_prepare_dt` rejects the minimal DTB, or fills it differently from what the layer expects | M | L (fails before anything runs) | not every fix-up was read (DESIGN 4.1) | rung L0: dry run, prepared FDT read back and parsed by the layer's own code on the host; fallback upstream DTB with `--dtb` | L0 |
| R-4 | An unknown or left-over FIQ source storms EL2 (a source we do not know how to clear) | L-M | M | no register names the FIQ cause; the known list is the same in Linux and m1n1 [verified: F0] | per-core clean-up at init (guest timer controls reset before the gates open), cause counters, spurious budget → fatal with a dump on screen | L2 (boot core), L5 (all cores) |
| R-5 | The maintenance interrupt (FIQ or IRQ: Linux checks it in its IRQ handler, so the signal type is [hypothesis] until measured) cannot be silenced by the harvest in some list-register state (it is not maskable) | L | M | KVM needed special handling for it [verified: L:drivers/irqchip/irq-apple-aic.c:406-421, 887-890] | DESIGN 5.2 step 3: check on both exit tails (IRQ 9 and FIQ 10); clear `ICH_HCR[7:1]`, re-read `ICH_MISR`, then `En = 0` and fatal; count, never loop; trap mode needs maintenance only for overflow | L3-L4 |
| R-6 | Position independence: a relocation type other than `R_AARCH64_RELATIVE`, a GOT entry, or an absolute literal used before relocation slips in | M | M (the boot core dies before any output) | new build mode for this code base | build check on the ELF's relocation types and on `start.S` literals; QEMU always runs relocated (link address 0); rung L1 isolates it on hardware | PLAN S6; L1 |
| R-7 | Cache incoherence at the MMU-off/MMU-on boundaries on real hardware: the spin-table release word, images written by the proxy, the relocated image, `.bss`/stacks, page tables written with the MMU off | M | M-H (random early failures) | QEMU TCG has no caches; the existing maintenance code is [hypothesis] on hardware [verified: R:el2/boot/README.md "Open points for the real M1"] | explicit clean/invalidate at every boundary (DESIGN 2.3, 3.3); checkpoints 0 and 1 bracket the MMU switch; L5 isolates the secondaries | L1-L2, L5 |
| R-8 | A secondary enters the layer in a state we did not expect (m1n1 MMU on, different DAIF, not in WFE mode) | L | M | read from source, not observed [verified: M:src/smp.c:60-106, M:src/memory.c:588-634] | `secondary_entry` masks DAIF and assumes nothing; a core that does not report within a timeout makes `CPU_ON` fail visibly, never hang | L5 |
| R-9 | Proxy ABI mismatch between the proxyclient (`main` of 2026-11-10) and m1n1 v1.6.1 for `kboot_*`; or the `kboot_boot` reply is lost and the script misreports | L-M | L (fails at L0, or is cosmetic) | day 1 used only reads, SMP start and calls [verified: HW header] | L0 dry run; the loader treats a lost reply after `kboot_boot` as success; fall back to a proxyclient of the v1.6.1 tag (a download on the host: Ciani's confirmation) | L0, L1 |
| R-10 | Guest RAM bookkeeping: a reserved range (m1n1, its stacks, the FDT, the ADT) leaks into the guest, a `/memory` range lies wholly inside a reservation, or the stage-2 pool overflows on the real memory map | L | M | the j293 map has unaligned ends [verified: HW boot log]; m1n1 adds reserved regions back as extra `/memory` ranges [verified: M:src/kboot.c:386-440] | 32 MB coarse rounding (DESIGN 4.3), host tests with a j293-shaped FDT including a fully reserved range, and at L0 with the real prepared FDT; pool exhaustion is already fatal with a message | PLAN S7-S8; L0, L3 |
| R-11 | Emulated GICD/GICR windows at `0xF_0000_0000` / `0xF_1000_0000` collide with something | L | M | below the 36-bit limit; not checked against the ADT | read-only ADT walk on day 2 before L3 (same method as HW row 7) | day 2, before L3 |
| R-12 | The watchdog reset sequence does not reset, or resets into recovery | L | M (L1 depends on it) | the sequence is m1n1's own reboot [verified: M:src/wdt.c:50-61] | L1 is exactly this test; from L2 on, if no restart within 5 s the layer prints "reset failed, halted"; power button | L1 |
| R-13 | Repeated forced power-offs put the Mac into a recovery/diagnostic start | L | L | m1n1's proxy set-up resets a panic counter [verified: R:docs/FAILURES.md F-29]; semantics [hypothesis] | boot macOS between sessions; DFU revive is the last resort and is still unproven (F-29) | experience |
| R-14 | The serial kit is wanted but conflicts with the host's zero-footprint rule (`sudo`, build), the cable is not SuperSpeed, or the port assumptions are wrong | M | L | [verified: D:hw/soc/serial-debug.md]; ports and the non-rebooting command are [check] | optional; framebuffer first; the people decide in T8 | people |
| R-15 | SError at EL2 from the M1's locally generated SEI in some list-register state, even with the traps on | L | M | SEIS = 1 [verified: HW row 3]; KVM's answer is the traps | the SError vector prints `ESR_EL2` and the `ICH_*` state; no untrapped mode on the M1 | L3-L4 |
| R-16 | The layer grows a second, untested code path per platform and QEMU coverage erodes | M | M | most M1 code cannot run on the bench | one binary, platform chosen from the FDT; host tests with fakes for every M1 module; the same guest binary on both platforms; `trap-notc` and the vendor hypercalls run in QEMU | PLAN rules |
| R-17 | A wrongly assembled Apple system-register encoding (an `S3_x_Cy_Cz_w` name typed wrong) touches another IMPLEMENTATION DEFINED register on hardware | L | M | none of these registers exists in QEMU, so the bench cannot notice | build check: disassemble the object with `llvm-objdump` and compare every Apple encoding with the table in DESIGN 5.1 | PLAN S10 |
| R-18 | The guest uses pointer authentication and traps, or the layer forgets `HCR_EL2.API/APK` on a secondary | L | M | m1n1 runs with both bits set [verified: HW row 4]; the layer does not set them today | set in the shared `g_hcr`; guest check G3 on every core that starts | PLAN S13; L3, L5 |
| R-19 | Identifying data (serial number, MAC addresses) ends up in a log, a photo or a commit | L | M | m1n1 writes them into the FDT [verified: M:src/kboot.c:454-525] | the layer never prints those properties; FDT dumps stay in the host folder (DESIGN 4.3) | PLAN S7, S17, S18 |

## 2. Open questions

| ID | Question | Current answer | Who / when |
|---|---|---|---|
| Q-1 | Do the `ICC_*` traps behave on the M1 as on QEMU: the `TALL1` group (precedent: KVM), the `TC` group (no precedent)? Does `ICC_SRE_EL1` read as SRE = 1 at EL1 without a trap? | [hypothesis] yes for `TALL1`/`TDIR`; open for `TC`, with `trap-notc` as the fallback (R-1a, R-1b) | L3 |
| Q-2 | Why did m1n1's EL1 call on cpu7 hang on day 2 with IRQs masked and a list register armed? | unknown; SError (SEIS) is a candidate [hypothesis] | L3 may explain it (the guest has vectors for every exception class and reports) |
| Q-3 | Does m1n1 accept the minimal DTB, and does it fill `/chosen/framebuffer` when the node starts as `status = "disabled"` with no `reg`? | [hypothesis] yes | L0 |
| Q-4 | Exact board compatible string m1n1 expects for an appended FDT (`apple,j293`?) | [hypothesis]; irrelevant for the proxy path | when path B is built |
| Q-5 | What does the built-in panel show after m1n1's framebuffer shutdown, and is the format really `x2r10g10b10` with the stride in the FDT? | [hypothesis] last image stays; format from m1n1's own mapping of depth 30 | L2 (format and stride already at L0, from the read-back FDT) |
| Q-6 | Do Windows and EDK2 look at `ID_AA64PFR0_EL1.GIC`? | [hypothesis] at least EDK2 does; the TID3 override makes the question moot | T11 |
| Q-7 | Is anything mapped at `0xF_0000_0000`-`0xF_1100_0000` on the j293? | [hypothesis] no | day 2, read-only |
| Q-8 | `SYSTEM_OFF`: is there a register-level power-off, or only the SMC? | [hypothesis] SMC only; halt for now | M3b |
| Q-9 | Does the test guest need the cores at more than their boot frequency (no `cpufreq_init`)? | [hypothesis] no | L5 timing |
| Q-10 | Should the first boot also be offered in a "return to m1n1" mode (the layer saves m1n1's EL2 state, runs the guest on one core, restores and returns, so the host can read the RAM log ring over USB)? | not in the plan: it adds restore code used only for tests; reconsider if R-2 materialises and no serial kit is available | Marco, after L2 |
| Q-11 | Does the serial kit get approved for Ciani's Mac (R-14)? Which ports, and does `macvdmtool serial` switch the pins without a reboot? | open; [check] | Marco + Ciani, before day 2 |
| Q-12 | Real `CPU_OFF` (power-down and restart through RVBAR) and idle states | deferred; the park loop is enough for Windows to boot **[hypothesis: Windows does not require cores to lose power]** | later milestone |
| Q-13 | Can the loader capture m1n1's `FDT prepared at …` console line to read the FDT back? | [check]; if not, the address is typed in by hand from the proxy console | L0 |
| Q-14 | Does the `kboot_boot` proxy request get a reply before m1n1 shuts its USB down? | [hypothesis] not reliably; the loader tolerates both | L1 |
