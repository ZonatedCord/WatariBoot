# RISKS and open questions (watari-winram)

- Project: Watari Boot, subsystem "watari-winram" · Date: 2026-11-14 · Version: 0.2 · Status: draft, reviewed once
- Linked documents: [README](README.md) · [DESIGN](DESIGN.md) ("D n") · [PLAN](PLAN.md) · [draft ADR](../../adr/draft-winram.md)
- P (probability) and I (impact): L / M / H, the author's estimate **[hypothesis]** in every row. "Settled by" names the plan step or rung that turns the item into a fact. Short source names as in DESIGN 0; "EDK2 R-E n" are risks of [watari-edk2-m1](../watari-edk2-m1/RISKS.md).

## 1. Risks

| ID | Risk | P | I | Why we think so | Mitigation | Settled by |
|---|---|---|---|---|---|---|
| **R-W1** | **bootmgr refuses a boot device whose path contains a RAM-disk node** (`RamDisk(...)/HD(...)`) | M | H (no Windows at all by this route) | Microsoft asks for Block I/O + Device Path only [verified: MS-UEFI "Local storage boot"]; how bootmgr maps device paths to its devices is not public **[hypothesis]** | bench first (T22); the builder's `--superfloppy`/`--mbr` layouts (`tools/m3a/build-winram-image.sh`) as a cheap first variant; contingency C-1: a parent device path that looks like a controller (the `Register` call accepts one) or an own Block I/O driver with a vendor node; contingency C-2: an own `SimpleFileSystem` over the files, the way iPXE's wimboot feeds bootmgr [verified: WIMBOOT], but that is a rewrite and GPL code must not be copied | T22 |
| R-W2 | The ISO's BCD does not resolve on our image (a device element is not boot-relative, a path differs) | M | M | not inspected on purpose; install media BCDs are described as `[boot]` relative **[hypothesis]** | bench first (T22); fallback = a BCD made with `bcdedit` in the bench Windows VM per MS-WALK step 4, kept on the data disk | T22 |
| R-W3 | The proxy is too slow (below 1 MB/s) or the Python checksum dominates | M | M (a 12-60 min wait per attempt; hardware days are short) | nothing measured; per-slice Python checksum **[hypothesis]**; `writemem` streams in 8192-byte writes [verified: M1N1 proxy.py] | the rate test (first step of W1) measures before anything else; negotiate `DISABLE_DATA_CSUMS` if the client allows; slice size tuned; a hand-trimmed image (saves 2 %); if still above 15 min, stop and ask Marco (Q-W3) | W1 (rate test) |
| **R-W4** | Windows' boot manager or BasicDisplay does not accept (or mis-draws) the GOP: truthful `PixelBitMask` 10-bit, or `--bgr8` on the 10-bit panel | H (EDK2 R-E1) | M-H (a blind boot; stop codes cannot be read) | Microsoft: BGR8 only [verified: MS-UEFI] | the bench answers it with the fake framebuffer in three configurations (T22); hardware starts with `--bgr8`; shadow framebuffer remains Marco's decision | T22, W1 |
| R-W5 | The multi-core, interrupt-heavy Windows kernel finds a bug in the layer on the M1 (IPI storm, a lost timer FIQ, `CPU_ON` of a core not started by m1n1, `trap` cost) | M | H (a hang at HAL init or in the first seconds) | EDK2 on hardware is uni-core; Windows 4-core runs passed on QEMU only [verified: R:docs/STATUS.md M2] | day-3 rung D4 (`--smp`, `trap-notc`) must pass first; W2 uses the same flags; the layer's per-core statistics are on the ticker | D4, W2 |
| R-W6 | RAM budget: 704 MiB source + about 650 MB bootmgr ramdisk + WinPE working set on an 8 GB M1 (guest "somewhat under 7.5 GB" [verified: EDK2 D 5]) | L | M | arithmetic: about 1.4 GB peak, WinPE base needs 512 MB [verified: MS-PE] | (T22: with Reserved the source copy is NOT returned, about 700 MB stay lost, since `EfiBootServicesData` does not work); a hand-trimmed image | W2 |
| R-W7 | The carve leaves the first `/memory` piece below PrePi's 128 MB / 64 MB-region rule, or the heap hands the blocks out in another order than assumed | M | M (a `FATAL` of the layer at D2-style start, nothing else harmed) | the allocator is first-fit from the low end [verified: M1N1 malloc.py v1.6.1]; the order the loader requests is its own code; the rule is verified [verified: R:el2/include/wel2_fdt_build.h `wel2_gfdt_place`] | the image block is allocated first; `gfdt_dump --ramdisk` and the D0 preview apply the same rule on the host before the jump | T21 (carve), T23 (loader order), D0 |
| R-W8 | The ramdisk range is mapped Device/uncached in EDK2's stage 1 or never mapped (GCD add without `SetMemorySpaceAttributes`), so EDK2 faults or reads stale data | L | M | the same GCD calls plus `Cpu->SetMemoryAttributes` that `HighMemDxe` makes [verified: HighMemDxe.c] | driver copies the pattern; bench log shows the CRC pass | T21 |
| R-W9 | **CONFIRMED in effect (T22, F-35): `EfiBootServicesData` gives `MEMORY_MANAGEMENT 0x1A`; mitigation applied, default is now Reserved.** Windows reclaims the `EfiBootServicesData` range **before** it has finished with the source (e.g. the SDI ramdisk is mapped in place, not copied) | L | H | MS-WALK and WIMBOOT describe a copy into a RAM disk [verified]; "appends the WIM to the template ramdisk" | switch `PcdWatariRamDiskType = Reserved` (accepts the NFIT and the `ACPI0012` SSDT that `RamDiskDxe` adds, loses 700 MB) | W2, bench |
| R-W10 | Stale data: the loader's writes sit dirty in m1n1's caches; EDK2 (MMU on, WB) reads old RAM | L | H (corrupt image; a CRC failure, not silent) | `dc_cvau`/`dc_cvac` over the range + m1n1's `mmu_shutdown` flush [verified: R:tools/m3a/watari-load.py] | the trailer CRC; D0 reads back a sample of the block through the proxy before the jump | W1 |
| R-W11 | The 1 GiB `ProxyUtils` heap cannot hold the image next to the other blocks, or its region is not usable RAM | L | M | 704 MiB + about 100 MiB of blocks [verified: M1N1 proxyutils.py: 1 GiB heap] | loader refuses an image above 896 MiB (DESIGN 2.3); `heap_size` argument; the whole-range block check | T23, D0 |
| R-W12 | WinPE/Setup needs an input device or a TPM/RAM/Secure Boot answer that stops it before the first Setup screen | M | L | Setup checks hardware ("meets the minimum requirements" error mentioned for missing WMI/SecureStartup components [verified: MS-PE]); no input devices exist | the first Setup screen is the milestone; later screens are not required; no keyboard (R-E14 of EDK2) | W3 |
| R-W13 | `EFI_RNG_PROTOCOL` has no entropy source on the M1 (EDK2 R-E17), and winload needs it | M | M-H | Microsoft: mandatory [verified: MS-UEFI Requirement 26]; `RngDxe` is in the firmware [verified: R:WatariM1Pkg.fdf:105] but its source on the M1 is unmeasured | read `ID_AA64ISAR0_EL1.RNDR` read-only on the next hardware day (EDK2 Q-E9); the bench's RNG (QEMU) says nothing about it | W2 |
| R-W14 | Licence and distribution: the image holds Microsoft files from Marco's own ISO | L | H | ADR-0005: no Microsoft binaries in the repository | the image and the staging folder live only on the data disk; the tool refuses an output path inside the repository; `.gitignore` lists `*.img`; the PR text never includes ISO content; nothing is analysed (F-01) | T23 |
| R-W15 | Thermal/power: eight busy cores for minutes on a firmware with no power management | L | L-M | m1n1 sets no DVFS beyond `cpufreq_init`; the fan is SMC-driven **[hypothesis]** | short rungs, a stop criterion at the first sign of a hot case; abort by the power button | W2 |
| R-W16 | Observability: no serial, no debugger; a hang after `ExitBootServices` shows nothing | H | M | no debug port [verified: EDK2 R-E13] | the layer's ticker keeps running (its own band in `wel2.fb=band`, **not** in `guest` mode); first hardware attempts use `band` where the GOP leaves enough rows; guest-mode run only when `band` passed | W1-W3 |
