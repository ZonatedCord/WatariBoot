# Session 2026-11-16, Marco 01: Monday review, catch mode, handoff

## What happened
- Reviewed Ciani's Monday bundle and PR #90. Day-3 gate PASS. W2 and W1c stopped with an EL1 synchronous exception, ESR 0x02000000 (EC 0 = UNDEFINED), just after BDS started `BOOTAA64.EFI`.
- Monday's firmware was the right one: the FD hash in the logs (`a8cf6ee11e591b4c`) is `WATARI_M1_EFI-bgr8.fd`.
- DxeCore symbolization [verified]: the two PCs on the screen are return addresses. `+0x25744` is in `_CModuleEntryPoint`, and `+0x1ECA4` follows the `blr` in `CoreStartImage`. The fault is inside bootmgr at 0x9BED00?4.
- The EDK2 RNDR use is guarded by an `ID_AA64ISAR0` check, so it is not the cause.
- Lead [hypothesis]: bootmgr reads a register the M1 does not implement, most likely the PMUv3 (`PMCR_EL0`). bootcamparm.com's public log (3 Nov) mentions "stop before the PMCR_EL0 read".
- W2 only: the guest got `memory@806000000` (a 32 MB gap between m1n1 reservations, which appears with secondaries=True). USB DART tables sit at 0x806f7c000 and 0x807458000 in the E log. This is an open risk; W1c did not have it.

## Update before the afternoon hardware run
- Bench (QEMU TCG, WinPE from RAM disk, `wel2.catch=pmu`): bootmgr's first accesses are PMCCNTR_EL0 and PMCR_EL0. The layer traps and emulates them.
  - RAZ PMU made bootmgr spin on PMCCNTR.
  - A running global virtual counter got Windows to the logo, then CRITICAL_PROCESS_DIED. The guest's PMUSERENR write was trapped, so the hardware register stayed 0, and EL0 PMCCNTR reads were UNDEFINED.
  - Mirroring PMUSERENR to the hardware fixed it: Setup "Attendere" at about 160 s (run `vp4`). Without catch (`base0`) Setup also appears.
- The mirror is only done when ID_AA64DFR0_EL1.PMUVer says PMUv3 exists (commit eeff338). On a core without PMUv3, the write would be UNDEFINED at EL2.
- Open on the M1 [hypothesis]: without PMUv3, MDCR_EL2.TPM may be RES0. Then the kernel-phase PMU accesses (EL1 and EL0) stay UNDEFINED, and only bootmgr/winload are covered by the EDK2 EL1 safety net. `ID0` and the first jump's "trap bits that did not stick" line decide it.

## Evening: after Ciani's afternoon run (PR #91)
- Faithful bench (`wel2.vpmu=undef` reflects PMU accesses to EL1 as UNDEFINED, as on the M1): the EDK2 EL1 net handles the first PMCCNTR read. Then bootmgr installs its own VBAR_EL1, and its handler spins at 0x7dec2a0c on the next UNDEF. This is the M1 stall [verified: bench nf3]. The EL1 net cannot cover anything after that point.
- Layer fix: HACR_EL2 (S3_4_C1_C1_7) bit 56 on the M1 (`wel2.hacr`, default 1<<56). EC 0x3F is decoded via AFSR1_EL2 (with guards), and PMU accesses go to the virtual PMU. Any other access is reflected as UNDEF. A fixed panel status row was added. Bit 56 is [hypothesis] until measured; see `docs/design/watari-el2/hacr56-pmu.md` and `re/m3b-other-projects-lessons.md`.
- Proxy rung HACR0 (no jump): writes bit 56, reads it back, and restores it.
