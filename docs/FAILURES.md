# Failures and lessons learned

This file collects everything that did **not** work, why it did not work and what we learned. It is meant for us and for anyone who tries something similar: a documented dead end saves weeks for whoever comes next.

Format of each entry:
- **What we tried** and **what happened**, with the evidence (logs, files, links);
- **why** (verified or hypothesis);
- **lesson** for the reader.

---

## F-01 · Analyzing the Windows binaries (ntoskrnl/HAL) for Phase 0 (2026-10-12)
- **Tried:** delegating to an agent the download of ARM64 `ntoskrnl.exe` with the public symbols, to analyze it with Ghidra.
- **What happened:** the task was stopped by a safety filter while it was being written.
- **Lesson:** Phase 0 was rethought as experimental ("black box": public documentation + experiments in QEMU), see the draft ADR "experimental Phase 0". A similar project must account for this methodological limit from the start.

## F-02 · Restarting from NTASP's work (2026-10-12)
- **Tried:** evaluating the pioneering public project "NT for Apple Silicon" (NTASP) as a base.
- **What happened:** it is not native (it uses the m1n1 hypervisor with emulated vGIC and PSCI), which did not fit our native-first goals; the AIC HAL extension is not implemented yet ("Nothing's implemented yet"); the AICv1 driver is still a stub (early-stage, actively developed); we found an issue in `AIC_MASK_BIT` (reported as a courtesy: NT-for-ASi/apple_silicon_platforms_mu#23).
- **Lesson:** before building on other people's code, check that its design fits your goals and not only that it exists (`re/ntasp-quality-audit.md`). Decision: independent route (ADR-0007).

## F-03 · "Just don't use FIQs" (ADR-0004), 2026-10-12/13
- **Tried:** designing an M1 in which Windows receives everything as IRQ.
- **What happened:** the **M1's ARM architectural timer is wired to FIQ only** (DTS `t8103.dtsi`, `AIC_FIQ`). There is no documented way to get it as IRQ, and macOS itself uses it as FIQ. The `ACC_OVRD_CONVERT_SIQ_TO_IRQ` bit exists in m1n1 but nobody has ever used it (`re/f0-m1-fiq-irq.md`, `re/f0-timer-irq-hw.md`).
- **Lesson:** the "no FIQ" hypothesis was wrong from the start for the timer. The remaining leads are in `docs/adr/draft-timer-fiq-strategy.md`.

## F-04 · The Raspberry Pi 3 precedent as proof (2026-10-13)
- **Tried:** using Windows on the Pi 3, which has no GIC, as proof that a non-GIC controller can be supplied from outside.
- **What happened:** the BCM2836 support was **inside Microsoft's HAL** (`edk2-platforms` `Platform/RaspberryPi/AcpiTables/Madt.aslc:51-52`: "Windows 10 on Raspberry Pi 3 does not boot otherwise... value that Microsoft had in their IoT blobs").
- **Lesson:** "Windows runs on a chip without a GIC" does not mean "a third party can add a controller". See also F-05.

## F-05 · HAL extensions for interrupt controllers (2026-10-13)
- **Tried:** looking for an official mechanism by which a HAL extension provides the interrupt controller.
- **What happened:** according to the author of `Wack0/NtHalExts`, HAL extensions for interrupt controllers *"were added in 789x but removed again in 799x"*, i.e. removed before Windows 8 RTM. His `halextbcm2709` works by pattern-searching the internal non-exported functions, and is tested only on Windows 8 ARM32. The only modern public examples (i.MX) are timer and DMA.
- **Lesson:** there is no official route; what remains is the one "with internal functions", which is fragile (`re/f0-nthalexts-lead.md`).

## F-06 · Removing the GIC in QEMU for the experiments (2026-10-12)
- **Tried:** using QEMU `virt` without a GIC.
- **What happened:** `gic-version` accepts only 2/3/4/x-5/host/max; `-acpitable` applies only to i386.
- **Lesson:** in QEMU "non-GIC" can only be simulated in the ACPI tables, so the experiments give a reliable "no" but only a weak "yes". A real bench without a GIC requires an AIC model written by us (`re/f0-qemu-aic-models.md`).

## F-07 · Paths with spaces (2026-10-13)
- **What happened:** EDK2's `edksetup.sh` and the QEMU monitor's `screendump` command fail if the path contains spaces (the disk is called "Arthur Fonzarelli").
- **Lesson:** use the link `/tmp/watari-data` (created by `tools/env.sh`). Better to give working disks names without spaces.

## F-08 · HVF acceleration with our EDK2 (2026-10-13, **SOLVED** 2026-10-14)
- **Tried:** booting Windows in QEMU with `-accel hvf -cpu host`, `-M virt,gic-version=3` and our EDK2 `edk2-stable202608` (DEBUG, CLANGDWARF).
- **What happened:** it hangs on the TianoCore logo ("Start boot option"); the serial stops at `[Bds]BdsWait(5)` and one CPU stays at 100%. The same firmware with TCG works and reaches the Windows Setup.
- **Wrong hypotheses ruled out** (useful to anyone trying the same): RELEASE build, `kernel-irqchip=off`, `gic-version=2`, `highmem=off`, `-smp 1` and timer masking (IMASK); the provisional patch `edk2-timer-imask.patch` was discarded.
- **Cause (verified):** with `-cpu host` under HVF, the `ID_AA64PFR0_EL1.GIC` field is 0 (read in the firmware: pfr0=0x1101000010110011), even though the GICv3 interface is usable. `ArmGicDxe` (`GicV3Supported`) decides GICv2/v3 only from that field, so it loaded the **GICv2** driver on a GICv3: no IRQs (PMR=0, IGRPEN1=0), the virtual timer stayed pending and `BdsWait` waited forever. The EDK2 firmware bundled with Homebrew works instead (it is a different build).
- **Solution:** `tools/edk2-hvf-gicv3.patch`: GICv3 even if the platform declares a redistributor base (`PcdGicRedistributorsBase != 0`); it is applied by `tools/build-edk2.sh`. **Verified by Opus:** with HVF the Windows Setup appears (`logs/screens/win-hvf-180s.png`).
- **Lesson:** on Apple Silicon with HVF the CPU ID registers may not tell the truth about GIC features. The firmware must not trust only those. Possible report to EDK2 (to be decided with Marco).

## F-09 · Download rules violated by agents (2026-10-13)
- **What happened:** two subagents saved temporary files (a copy of the Linux source `aic.c`, the parking spec PDF) in Claude's internal folders, despite the download ban in the prompts. The backup was confirmed and nothing ended up in the repository.
- **Lesson:** bans in the agents' prompts are not enough. You must explicitly say "no temporary files" and check afterwards.

## F-10 · Black screen mistaken for a stuck installation (2026-10-14, false alarm)
- **Tried:** checking with `screendump` the automatic Windows installation (HVF, ramfb, no display).
- **What happened:** after ~2 hours the screenshot was completely black, the disk was no longer being written and the serial was silent: it looked like a hang. In reality Windows had finished and the screen had turned off due to inactivity.
- **Lesson:** before declaring a hang, send a key (`sendkey shift` from the QEMU monitor) and take the screenshot again. Serial silence says nothing about the Windows kernel (serial debugging was not yet active/verified).

## F-11 · Windows does not boot with acpigen's MADT+GTDT (qemu-virt model) (2026-10-14) — SOLVED
- **Tried:** firmware `QEMU_EFI-watari.fd` (driver `WatariAcpiOverride`, which at ReadyToBoot replaces MADT and GTDT with those from `acpigen -m qemu-virt`) and booting the installed Windows 11 (N2), with HVF, disk `snapshot=on`. Windows loaded `ntoskrnl.exe` and hung (CPU 100%, TianoCore logo). With the original firmware: desktop in under 2 minutes (`logs/screens/n4w-base.png`).
- **Cause (verified):** our MADT was missing the **GIC MSI Frame** (subtable type 0x0D, QEMU v2m at 0x08020000, SPI base 0x50, count 0x40). Without MSI, Windows cannot use the MSI interrupts of NVMe/xHCI and hangs after loading the kernel (explanation is a hypothesis; the effect is verified by the ablation below). The field-by-field comparison is in `re/f11-acpi-comparison.md` (original tables read from the guest RAM).
- **Outcomes of the hypotheses** (script `/tmp/watari-data/run-f11/t.sh`, 4 minutes, `snapshot=on`; "hang" = still on the TianoCore logo at 230 s):
  - H0 (repeating the problem, firmware as it was): hang. Reproduced.
  - H1 (parking disabled: version 0, address 0): hang on its own. Not the cause.
  - H2 (GICD before the GICCs like QEMU; GICD/GICR already identical in value): hang (H1+H2). Not the cause.
  - H3 (GTDT flags like the original: only NS EL1 ALWAYS_ON, rest 0): hang (H1+H2+H3). Not the cause.
  - H4 (layout/length errors): none in the GICC/GICD/GICR fields (same offsets and values). Benign differences: MADT revision 6 instead of 4, GICC of 82 bytes instead of 80, OEM ID.
  - H5 (new, found through the comparison): adding the GIC MSI Frame (and PMU GSIV 23 in the GICCs): **desktop/login screen in under 120 s**. Ablation: the MSI Frame alone (PMU 0) is enough (lock screen at 120 s). The MSI Frame with parking v1, GICD after the GICCs and all GTDT flags ALWAYS_ON (i.e. F-11's original model plus MSI) reaches the desktop: parking, ordering and GTDT flags are therefore irrelevant with PSCI on QEMU/HVF.
- **V1 succeeded:** `logs/screens/v1-ok.png` (desktop; the "Sticky Keys" dialog is caused by our `sendkey shift` to wake the screen, see F-10). Final model: parking 0, GICD first, PMU 23, GICR Structure, MSI Frame, GTDT like the original.
- **Lesson:** before hypothesizing, compare with the original tables. The dump is done with `pmemsave` from the QEMU monitor and a search for `RSD PTR ` in the RAM (no UEFI shell needed).

## F-12 · Driver build with a stale layout (2026-10-14)
- **Tried:** modified `acpigen_cpu`/`acpigen_madt_opts` in `acpigen.h` and re-ran `tools/build-edk2-watari.sh`.
- **Failed:** EDK2 does not detect changes to the acpigen headers (path outside PACKAGES_PATH): `WatariAcpiOverride.c` stayed compiled with the old layout of `acpigen_model`, so it read `Model->gtdt` at a wrong offset: "acpigen_build_gtdt error -2" or a wrong pointer and QEMU/HVF aborting (`Assertion failed: (isv)` in `hvf_handle_exception`, at about 7 s, during the firmware).
- **Remedy:** `tools/build-edk2-watari.sh` deletes the module's build folder before compiling. If you see the `isv` abort right after "MADT acpigen installata", first check whether the driver is stale.

## F-13 · V6: timer in Group 0 at ExitBootServices restored to Group 1 (2026-10-14)
- **Tried:** `WatariTimerFiqDxe` puts PPI 27/30 in Group 0 at ExitBootServices (IGROUPR0 -> 0xB7FFFFFF, `ICC_IGRPEN0`=1, `GICD_CTLR.EnableGrp0`); Windows 11 with `kernel-irqchip=off` and GIC trace.
- **What happened:** the write happens (serial and trace `0x10080 = 0xb7ffffff`).
- **Failed:** in the trace, right after (`IGRPEN1=0`, `ICENABLER0=0xffff00ff`) comes `IGROUPR0=0xffffffff`: PPIs back in Group 1, before the timer is enabled. Zero `hvf_inject_fiq`: no FIQ delivered, so it is not known whether Windows would tolerate the FIQ. In addition the control (V1 firmware) with `kernel-irqchip=off` does not reach the lock screen but Windows RE (slow boot, "automatic repair"), so the test bench is degraded.
- **Why (hypothesis):** a GIC re-init after ExitBootServices (firmware or Windows HAL) resets the groups; who does it has not been identified.
- **Lesson:** method A alone is not enough. First identify the writer of IGROUPR0 (e.g. a trace with timestamp and PC, or a hook in the monitor), and understand why `kernel-irqchip=off` degrades the Windows boot; then decide whether method B (QEMU patch, not to be built without Marco's go-ahead) is needed.

## F-14 · V2: MADT without GICD, Windows does not reach the session (2026-10-14)
- **Tried:** acpigen model `qemu-virt-nogicd` (like qemu-virt: 4 GICC + GICR Structure + MSI Frame, **no GICD Structure**; MADT 412 bytes instead of 436), firmware `QEMU_EFI-watari-nogicd.fd` (`tools/build-edk2-watari.sh --nogicd`). Windows 11, HVF, default kernel-irqchip, `-smp 4`, `snapshot=on`, 240 s. Script `/tmp/watari-data/run-g2/t.sh`.
- **Result (verified):** the serial shows "MADT generata da acpigen: 412 byte, 4 CPU" and the replacement; Windows loads `ntoskrnl.exe` and then the screen stays identical (same hash) from 20 s to 220 s: still on the UEFI text/TianoCore logo (ramfb is no longer updated), no lock screen (V1, with the GICD, reaches it at 120 s), no visible bugcheck, no reset. Screenshots `docs/img/v2-nogicd-100s.png` and `v2-nogicd-220s.png`. It is the same symptom as F-11 before the MSI Frame.
- **Interpretation:** Windows **requires the GICD in the MADT** (confirms risk R-02). Limit: a hang, not a bugcheck code, so it is not known what the kernel is doing (probably the HAL/GIC init fails without the distributor base; hypothesis). A single 240 s run, without a parallel control (the V1 control is F-11).
- **Lesson:** on a SoC without a GICD (AIC) you must either provide a dummy/compatible GICD or write the HAL extension that replaces the GIC; the MADT without a GICD alone is not enough.

## F-15 · V3: parking protocol without PSCI, Windows uses it but bugchecks with HAL_INITIALIZATION_FAILED (0x5C) (2026-10-14)
- **Tried:** firmware `QEMU_EFI-watari-park.fd` (WatariParkingDxe + MADT parking v1 + FADT with PSCI_COMPLIANT=0), `-smp 4`, Windows 11, HVF, `snapshot=on`.
- **Verified:** serial: 4 mailboxes (0x46300000, 0x462F0000, 0x462E0000, 0x462D0000), `CPU_ON` cpu1..3 -> PSCI 0, FADT installed with PSCI=0, MADT 436 bytes with parking v1. About 17 s after boot Windows **writes** to CPU1's mailbox: `ProcessorId = 1` and `JumpAddress = 0x110af7010` (seen by the stub, which copies it to +0xFF8 before zeroing it as an ack). The mailboxes of CPU2 and CPU3 are never touched. About 15 s later (at ~32 s) bugcheck **HAL_INITIALIZATION_FAILED (0x5C)** with automatic reboot, in a loop (then "Preparing automatic repair"). Screenshot `docs/img/v3-bugcheck-hal5c.png`. Evidence: `/tmp/watari-data/run-v3/` (mbs.log, mb-v3c-*.bin).
- **Decisive outcome:** Windows ARM64 **uses the parking protocol** (it does not ignore it) even without PSCI, but the start of the first AP fails and the HAL does not initialize. No lock screen, so no measurement of the visible CPUs.
- **Why (hypothesis, to be verified):** CPU1 jumps to Windows' address but does not complete the handshake: the stub left the AP in a state Windows does not expect (X0 = mailbox address and not something else; cache/MMU; GIC/system registers; Processor ID read differently by Windows), or Windows waits for a wake-up SGI/IPI that the stub does not handle. The trace does not yet have the AP's PC (`info cpus` under HVF does not show the PC).
- **Lesson:** the V3 test is useful and the parking is recognized; the next step is to understand what Windows expects from the AP after the jump (GIC trace for the SGI, disassembly of Windows' stub at 0x110af7010 in the RAM dump, register state required by Microsoft's parking v1 spec).

### F-15, attempt A (last time-boxed attempt, 6 QEMU tests, 2026-10-14, branch `marco/a-ultimo-tentativo`)
Tools: `WATARI_PMODE` bits (build `--parking`; 1 FADT PSCI+HVC, 2 MADT without parking, 4 no CPU_ON, 8 stub without GIC, 16 no redistributor wake, 32 GPRs zeroed at the jump), stub diagnostics in the mailbox (+0xF00..0xF30), QEMU's gdbstub (`-gdb`, works under HVF: it returns GPRs and PC, NOT the updated system registers) and GIC trace with `kernel-irqchip=off`. Scripts and evidence in `/tmp/watari-data/run-a/` (`t.sh`, `gdbregs.py`, `trace-t6.log`, `mb-*.bin`, `shots/`).
- **H1 control (T1), RULED OUT as the cause:** acpigen FADT with PSCI_COMPLIANT|USE_HVC (arm_boot_arch=3) + MADT with parking_version 0, no CPU_ON from us: Windows reaches the lock screen (`docs/img/a-t1-controllo-fadt-psci-lock.png`, ~100 s). Our FADT is good; the 0x5C is tied to the parking. Limit: it was not measured how many CPUs Windows sees.
- **H2 core state at the jump (T2), RULED OUT:** the stub records the entry: CurrentEL=EL1 (HVF without virtualization, as the spec requires), SCTLR_EL1=0x30900180 (MMU/cache off), DAIF=0x3c0, MPIDR 0x80000001/2, ICC_SRE_EL1=7 already at entry, PMR=0, IGRPEN1=0. All conformant to Table 1 of the spec. With X0 = mailbox Windows really jumps: the AP arrives in kernel code (VA 0xfffff80...), cpsr 0x800003c5 (EL1h, DAIF masked). The mailbox contains the AP boot block prepared by Windows (+0x10.. TTBR/TCR/MAIR, +0x330 = VA of the start routine): the AP's PC is always routine+0x200, in 4 different boots (T2, T3, T5), so it is stopped in a short wait (WFE/WFI or a short loop), not crashed in a random exception.
- **H3 stub's CPU interface/GIC (T3, T5), RULED OUT:** stub without touching ICC, redistributors not woken by us, GPRs zeroed (PMODE=56): the AP stays stopped at the same point (+0x200). So it is not our GIC init (PMR=0xFF/IGRPEN1) that blocks it. Beware, measurement artifact: stopping and resuming the VM with gdb (T3, T5) makes the bugcheck disappear (screen stuck on the UEFI text up to 220 s): the BSP's timeout cannot be observed with gdb.
- **H3b wake-up interrupt / in-kernel GIC (T6), the idea "bug in HVF's in-kernel GIC" RULED OUT:** with `kernel-irqchip=off` (GIC in userspace) the 0x5C repeats (0x5C screens and boot loop). GIC trace, repeated at every boot: (a) the BSP (cpu 0) does its ICC init (IGRPEN1=0, PMR=0, IGRPEN1=1, PMR=0xF0); (b) cpu 1, after the jump, does IGRPEN1=0, PMR=0, `GICR1 ICENABLER0=0xffff00ff`, `GICR1 IGROUPR0=0xffffffff`, IGRPEN1=1, and then **writes nothing more** (the PMR=0xF0 that the BSP writes right after IGRPEN1=1 is missing); (c) the only SGIs generated are SGI 0 from cpu 0 with targetlist 0x1 and affinity 0, i.e. to itself (1 per boot): **Windows sends no SGI/IPI to cpu 1**, neither as a parking "doorbell" nor afterwards.
- **H4 CPU2/3 never touched:** consistent with the above: Windows starts one AP at a time and waits for the first to complete the handshake; AP 1 stays stopped and after ~15 s the BSP bugchecks. Nothing says that CPU2/3 are the problem.
- **Cause NOT found.** Status: the parking is recognized and the AP enters the kernel, but it stops in a wait right after its GIC init, and the BSP sends it no interrupt. Main suspicion [hypothesis, not proven]: the AP waits for an event/flag from the BSP (WFE/SEV on memory, or an interrupt that in the PSCI path arrives through another channel) and the BSP waits for the AP: deadlock. Other live hypotheses: the mailbox page mapped by Windows as Device while the AP reads it cacheable (coherency); the AP block waiting for something that with PSCI is already in the context_id.
- **Next steps (require more tests, the budget of 6 is over):** (1) identical trace (`kernel-irqchip=off`, same events) with the T1 control firmware (PSCI FADT, the cores are started by Windows): if in that case cpu 1 writes PMR=0xF0 and proceeds, the comparison tells what is missing; (2) reading the instruction at the AP's PC (routine+0x200) to know whether it is WFE/WFI or a loop on memory: this requires looking at Microsoft code, hence Marco's decision (rule "no analysis of Microsoft binaries"); (3) try to send an SGI to cpu 1 ourselves from the BSP stub/firmware after the jump (hack: repeat SEV/SGI from a driver).
- **Lesson:** `info registers`/sysreg via gdb are not updated under HVF (only GPRs and PC), and stopping the VM distorts the guest's timeouts: for timing tests use only GIC traces and `pmemsave`.

## F-16 · WatariParkingDxe: ASSERT in InvalidateInstructionCache (2026-10-14)
- **Tried:** `--parking` firmware built by task G4; booted with DEBUG.
- **Failed:** `ASSERT [WatariParkingDxe] ArmCacheMaintenanceLib.c(47)`: in `ArmCacheMaintenanceLib` the `InvalidateInstructionCache()` without a range is an `ASSERT(FALSE)`; G4's driver called it after preparing the mailboxes, so the firmware stopped at the driver load (no boot).
- **Remedy:** `InvalidateInstructionCacheRange(P, SIZE_4KB)`. Build redone (FV always 48 bytes free, it fits).
- **Lesson:** G4 had been verified only by building; drivers must be booted at least once. In DEBUG, the "whole cache" functions of ArmCacheMaintenanceLib are ASSERTs: always use the Range variants.

## F-17 · M0-C: `__image_start` in a subtraction inside the assembler (2026-10-15)
- **Tried:** arm64 Image header with `.quad __image_end - __image_start` (both linker-script symbols) in `start.S`.
- **Failed:** clang's integrated assembler: "symbol '__image_start' can not be undefined in a subtraction expression" (verified).
- **Remedy:** compute `__image_size = __image_end - __image_start` in `linker.ld` and reference that single absolute symbol from the assembly.
- **Lesson:** the assembler cannot subtract two external symbols; let the linker script do arithmetic on layout symbols. Also: macOS has no `timeout(1)`, so `run-qemu.sh` implements its own 20 s watchdog.

## F-18 · M1-1: alignment fault at EL2 when linking the vGIC model (2026-10-19)
- **Tried:** linking `el2/vgic/vgic.c` into the freestanding EL2 image (EL2 MMU off).
- **Failed:** `ESR_EL2=0x96000061` (DFSC 0x21, alignment fault) inside `vgic_reset`: clang merged adjacent byte/halfword stores of the packed `vgic_irq` arrays into a 64-bit store at an odd address (`stur xzr, [x9, #-0x1f]`). With the MMU off all EL2 data accesses are Device memory, which does not allow unaligned access (verified in QEMU TCG).
- **Remedy:** compile the image with `-mstrict-align`. The proper long-term fix is an EL2 stage-1 identity map with Normal memory for RAM.
- **Lesson:** without an EL2 MMU every data access is Device; build EL2 code with `-mstrict-align`.
- **Update 2026-10-20 (#53, F-22):** EL2 now has a stage-1 identity map with Normal memory; only the MMU-off code and the EL1 payload keep `-mstrict-align`.

## F-19 · M1-2: QEMU cannot exercise the M1 SEIS erratum (2026-10-19)
- **Tried:** reading `ICH_VTR_EL2` in QEMU TCG (`virt,virtualization=on,gic-version=3 -cpu max`) to decide HW vs TRAP_EMULATE.
- **Observed (verified):** `ICH_VTR_EL2 = 0x90b80003`: 4 list registers, PRIbits 5, `SEIS=0`, `TDS=1`. The guest's `ICC_IAR1/EOIR1/PMR/IGRPEN1` work on hardware list registers with no trap; only `ICC_SGI1R_EL1` traps (EC 0x18, `IMO=1`).
- **Consequence:** the HW-LR mode proven here says nothing about Apple M1, where the erratum forces `TALL1`/`TC` (RISKS R-01). The ICC emulation path (TRAP_EMULATE) is still untested; it must be added and tested with `TALL1=1` in QEMU before M1 hardware (QEMU does implement the `TALL1` trap, so it can be run).
- **Lesson:** passing in QEMU HW mode is not evidence for the M1 mode. Design hazard caught in review, never hit: the maintenance PPI 25 is a level line, so the LRs must be freed before its EOI, otherwise the IRQ loop re-fires forever (`cpuif_irq`).

## F-20 · M1-3: SMP hazards found in design and review (2026-10-19)
None of these was hit in the final QEMU runs (`run-m1-3.sh` passes 7/7, with `thread=multi` and `thread=single`); they are recorded because each one was a silent hang or a wrong result waiting to happen.
- **WFI with no wake-up source.** A first draft of the payload's wait loop did `wfi` on the boot core while waiting for a flag set by another core: nothing ever interrupts that core, so a missed event hangs it for good (F-14). Remedy: `wait_flag()` masks IRQs, checks, then `wfi` only on cores that have a guaranteed wake-up (secondaries keep their 10 ms CNTV timer running while they wait for an SGI or the go-off flag); the boot core polls.
- **Cross-core kick storm.** Kicking a core that has a deliverable interrupt but no free list register is useless, and two cores in that state would kick each other forever from `cpuif_irq()`. `cpuif_kick_others()` skips cores without a free LR. The proper fix (`ICH_HCR_EL2.UIE` underflow interrupt, LR overflow handling) landed in #54 (F-22); the guard stays for cores whose LRs are full.
- **Spin locks on Device memory.** EL2 still runs with the MMU off, so `g_big`/`g_uart` (ldaxr/stlxr via `__atomic_exchange_n`) are exclusives on Device memory. QEMU TCG accepts them; the Arm ARM makes exclusives on Device memory IMPLEMENTATION DEFINED, so on Apple M1 this needs the EL2 stage-1 identity map with Normal WB memory first (same prerequisite as F-18) **[hypothesis, not tested on hardware]**. *Update 2026-10-20: the stage-1 map is on (#53, F-22), so the locks are exclusives on Normal Inner-Shareable memory; still untested on hardware.*
- **CPU_OFF of the last ON core is DENIED** (the spec allows it, PSCI 5.5; nothing could ever wake the system and QEMU would sit silently). Deviation chosen on purpose, documented in `psci.c`.
- **CPU_OFF -> CPU_ON race.** `state = OFF` is published before the firmware has really powered the core down; an immediate CPU_ON can get the firmware's `ALREADY_ON`. `cpu_on()` retries the firmware call (bounded) instead of failing. Not seen in the runs.
- **Secondary stack slot = MPIDR Aff0** (`secondary_entry`). Right for QEMU virt (Aff0 = core index, <= 8 cores), wrong for M1 (Aff1 = cluster). Needs a core-index table lookup in assembly before hardware.

## F-21 · M1-4: EDK2 under the layer, four dead ends before BDS (2026-10-20)
Context: `ArmVirtQemuKernel` (RAM-loaded EDK2) entered at EL1 by Watari EL2, `run-m1-4.sh`. Each item stopped the boot; none was a silent hang because the layer dumps every unhandled guest fault with x0-x30 (F-14).
- **Layer at the top of RAM (design said "layer region at the top, `/memory` size reduced"): QEMU refuses.** `qemu: Not enough space for DTB after kernel/initrd`. QEMU wants the DTB after the kernel, so a `-kernel` image with a large `text_offset` cannot sit at the top of a 2 GB machine. The layer stays at `0x40080000`, the head of RAM, and the `/memory` node loses its first 2 MB (base moved up, size reduced). INTERFACES 3.2 updated.
- **PrePi reads the FDT at `0x40000000` before it knows where the FDT is.** `DebugLibFdtPL011Uart` (`FdtSerialGetPorts`) calls `fdt_check_header(PcdDeviceTreeInitialBaseAddress)` from the first `DebugPrint`, i.e. inside `RelocatePeCoffImage`, before `DiscoverDramFromDt` updates the PCD. Upstream the default `0x40000000` happens to be where QEMU puts the DTB for this image. Symptom: stage-2 translation fault at IPA `0x40000000`, `ELR` inside `fdt_check_header` (found with `-d in_asm` + `llvm-symbolizer` on the PrePi `.debug`). Remedy: the layer copies the patched FDT (only the used 8 KB, `fdt_used_size`: QEMU leaves `totalsize` at its 1 MB buffer) to `0x40000000`, a 512 KB hand-off buffer that is mapped in stage 2 but not in `/memory`.
- **Stage-2 IPA space of 32 bits.** `PCI Bus First Scanning` took a data abort at IPA `0x4010000000` (the high PCIe ECAM of QEMU virt). IPA space is now 40 bits (`T0SZ=24`, start level 0, two 512 GB entries, 1 GB device blocks above 3 GB), which also covers the high PCIe MMIO window at `0x8000000000`.
- **EDK2 never wakes the redistributor, so the first timer tick vanished and the boot stalled at `BdsWait(3)`.** `ArmGicV3Dxe` has no `GICR_WAKER` handshake (it assumes TF-A or QEMU left the redistributor awake). The vGIC model resets with `ProcessorSleep=1` (as real hardware and as INTERFACES 3.1 said), so `vgic_next_pending()` returned nothing, the layer had already masked physical PPI 27 and nothing ever unmasked it: one timer interrupt, then silence for ever. Found by printing the model state at the first PPI 27 (`sleep=1`, `ctlr=2`, `flags=ENABLED|GROUP1|LINE`). Remedy: `vgic_vcpu_wake()` (host-tested) on the boot vCPU and on every vCPU started by PSCI in the chain build; INTERFACES 3.1 updated. Windows does the handshake itself, which is harmless on an awake redistributor.
- **Lesson:** a lost level interrupt is the worst failure mode of the "mask at the source, unmask on harvest" scheme: if the model cannot take the interrupt, the mask must not stay set. Open item: `cpuif_irq` should unmask PPI 27 again when `vgic_next_pending()` finds nothing deliverable (not done, the wake-up fixed the cause).

## F-22 · Hardening before M2: LR overflow, EL2 stage 1, TRAP_EMULATE (2026-10-20)
Issues #54, #53, #52. All three landed; these are the dead ends and design traps met on the way (QEMU TCG, `run-all.sh`, both modes pass).
- **A "no EOI maintenance" test knob hung the boot.** To exercise the underflow interrupt (UIE) on its own, the first draft of `wel2.test=noeoi` left the EOI bit (LR bit 41) out of *every* list register. The virtual timer (level PPI 27) then deadlocked: EL2 keeps the physical PPI masked until the guest's EOI is noticed, nobody noticed it (no maintenance interrupt, no exit), so the timer never fired again and `el1_irq_test` spun until the 20 s watchdog. Remedy: the knob only drops the EOI bit of SGIs (edge-like latches, nothing is masked on their behalf). **Lesson:** the EOI maintenance interrupt is not an optimisation for level sources, it is what unmasks them.
- **UIE alone is almost never what refills the LRs.** Each LR carries `EOI=1`, so every guest EOI already raises the maintenance interrupt and refills at once; `ICH_HCR_EL2.UIE` (zero or one valid LR) only fires when EOIs are not noticed. It is armed only while interrupts overflow and at least two LRs are valid, because with fewer valid LRs the condition is true at once and EL2 cannot clear it (storm). `NPIE` (no pending LR) was **not** used: it stays asserted while every valid LR is active, which EL2 cannot change, so it would storm. Without the knob the UIE count in `run-m1-5.sh` is 0 (verified); with it, 3 (verified).
- **Priority inversion with full LRs.** Filling only free LRs delivers a late high-priority SGI after the lower-priority ones already in the LRs. Remedy: a pending-only LR (never touched by the guest) is evicted with `vgic_requeue()` when a strictly better interrupt waits (`vcif_fill`, host-tested and `run-m1-5.sh` phase "eviction"). Not done: kicking another core to evict (that is the kick-storm guard of F-20: a core with full LRs is not kicked; it re-evaluates at its next exit).
- **`-mstrict-align` cannot be dropped everywhere.** With the stage-1 map on, `vgic.c` compiles without it and runs (the `stur xzr, [x8, #0x25]` of F-18 is back in the object code and works on Normal memory: that is the evidence the map is on). Kept per file for `stage1.c` (builds the tables with the MMU still off), `util.c` (UART/lock/format helpers, also called by the EL1 test payload with its MMU off) and `payload.c` (EL1, MMU off = Device memory).
- **The MMU switch must not touch the stack.** `s1_enable` is assembly with registers only; a C function that enables caches mid-way would read its saved return address through a cache that may hold a stale line of the stack written while the MMU was off [hypothesis, cannot be seen in TCG]. The FDT pointer is kept in x19 across the two calls.
- **EL2 writes are now cached; the guest starts with caches off.** The patched FDT copy is cleaned (`dc cvac` + `dsb ish`, `dcache_clean_range`) before the ERET to EDK2. TCG does not model caches, so a missing clean would pass the test and fail on hardware [hypothesis]; the original in-place patch of the QEMU FDT is not read by the guest and is not cleaned.
- **E2H.** The layer runs with `HCR_EL2.E2H = 0` (nothing sets it; QEMU resets it to 0), so stage 1 uses the E2H0 layout of `TCR_EL2` (PS[18:16], RES1 bits 31 and 23, AP[1] RES1). The E2H = 1 layout (EL2&0: IPS[34:32], EPD1, UXN+PXN, AP[1] = 0) is coded but never executed **[hypothesis]**; it is needed on the real M1 (stuck at E2H = 1, ARCHITECTURE 1.3).
- **TRAP_EMULATE fidelity (limits, F-19 still applies).** QEMU has `SEIS = 0`, so only the logic is tested, not the erratum. `ICC_HPPIR1_EL1` ignores PMR and the running priority (spec text only says "highest priority pending"; KVM-like) **[hypothesis]**. `ICC_CTLR_EL1` reports `IDbits = 0` (16 bits), `SEIS = 0`, `A3V = 1`. Group 0: `IAR0/HPPIR0` return 1023, `EOIR0` is a no-op (no Group 0 LR is ever filled). `PREbits > 5` is coded (AP registers 1..3) but only `PREbits = 5` ran.
- **Trapped `ICC_PMR_EL1` writes during the M1-4 EDK2 boot (input for #43): 1** (one write by the single core EDK2 uses; 998 `IAR1`/`EOIR1` pairs in the whole run, 4 other trapped accesses). This is EDK2 on QEMU, not Windows: the Windows figure is the M2 measurement.


## F-23 · M2: Windows 11 on top of Watari EL2, five dead ends (2026-10-20)
Context: `el2/boot/run-m2.sh`, the installed VM disk (`snapshot=on`) booted through EDK2 (`ArmVirtQemuKernel`) at EL1 on the layer, QEMU TCG. EDK2 finds Windows through the NVMe fallback boot option with no help (no `BOOTAA64.EFI` hunting needed). Evidence: serial logs and screenshots in `$WATARI_DATA/logs/m2/`.
- **PSCI over SMC, not HVC.** Windows takes the conduit from the ACPI FADT that QEMU builds, and with `virtualization=on` that conduit is SMC, while the FDT we patch for EDK2 says `hvc`. The layer treated every SMC as a stray one (`NOT_SUPPORTED`): Windows asked `PSCI_VERSION`, `PSCI_FEATURES` x9 and `CPU_ON` and got `-1`. Remedy: `handle_smc` hands PSCI function ids to the same `psci_handle` as HVC (`ELR` advanced by hand, non-PSCI SMCs still get `NOT_SUPPORTED`). **[verified: serial trace]**
- **`its=off` makes Windows hang in an INTx storm (my first choice, wrong).** I turned the QEMU GIC ITS off because our vGIC has no LPIs. Windows then enabled the NVMe INTx (SPI 5 = INTID 37) and the layer injected it ~7000 times per second for ever (`vIRQ injections` 0x692e03 against 0x186a0 timer ticks), the screen stays black after the TianoCore logo. **The same hang happens with no layer at all** (plain QEMU TCG, same firmware, disk and `its=off`: PC alternates between two kernel addresses, DAIF masked, serial silent for 20 min), and it disappears with `its=on` (plain QEMU reaches the lock screen in about 4 minutes, `-smp 1` and `-smp 4`). So the layer was not at fault; Windows on this QEMU needs MSI through the ITS. Whether the storm is a QEMU NVMe INTx quirk or a Windows INTx path problem is **not known [hypothesis: the Windows NVMe driver only supports MSI/MSI-X on this virtual GIC]**; not pursued. **[verified: control runs `ctl` vs `ctl-its-on`]**
- **LPI/ITS pass-through added to the vGIC.** With `its=on` the MADT carries a GIC ITS and Windows programs it. Design: the ITS frame is mapped in stage 2 (guest IPA = PA, no emulation, the physical ITS works on guest memory directly); the model exposes `GICD_TYPER.LPIS` + IDbits 16 and `GICR_TYPER.PLPIS`, keeps `GICR_CTLR.EnableLPIs/PROPBASER/PENDBASER` and forwards those writes, plus `INVLPIR/INVALLR`, to the physical redistributor of the same core (`lpi_reg` hook, `gic_phys_lpi_reg`); a physical LPI arrives at EL2 as an ordinary physical interrupt, its priority is read from the guest's property table and it is queued in a small per-vCPU list (`vgic_lpi_inject`, 64 entries, drops are reported) and injected through a list register like any other virtual interrupt. 5 host tests (`test_vgic_lpi.c`). Not done: LPI affinity changes behind the layer's back (ITS `MOVI/MOVC` are forwarded implicitly because the ITS is the physical one), `GICR_CTLR.RWP` polling is bounded, no limit on LPI queue overflow other than a log line. On Apple M1 this whole route is moot (no ITS: AIC), it only exists for the QEMU bench **[hypothesis for M1]**.
- **4 GB of RAM.** Stage 2 and EL2's own stage 1 only knew RAM up to `0xbfffffff` (the `-m 2G` of M1-4). Windows with `-m 4G` places `CPU_ON` entry points and the LPI property table above 2 GB (entry `0x1150f7010` seen). Remedy: stage-2 and stage-1 Normal blocks up to `0x13fffffff`.
- **`INTERNAL_POWER_ERROR (0xA0)` with `-smp 4`, never with `-smp 1`: `CPU_ON` returned `INVALID_ADDRESS`.** `cpu_on()` rejects entry points outside `GUEST_RAM_BASE..GUEST_RAM_END`; the end was still `0xc0000000`. Trace (`wel2.trace`): `CPU_ON` (SMC64 `0xC4000003`) cpu 1, entry `0x1150f7010`, ret `-9`; Windows bugchecks 0xA0 about 60 s after the logo, restarts, and after a few loops shows "Preparing Automatic Repair". With `GUEST_RAM_END = 0x140000000` all three secondaries come up and Windows reaches the lock screen with 4 CPUs. **[verified: trace before/after]** The bugcheck parameters were not read (blue screen hides them; we do not analyse Microsoft binaries).
- **Tooling traps.** (1) `screendump` in the QEMU monitor takes a path and the data disk has a space in its name: the dump silently never happens. Dump to a space-free temp dir and copy. (2) The "wake the display" `sendkey shift` of F-10, sent every minute, presses Shift five times and Windows shows the Sticky Keys dialog over the lock screen (cosmetic, seen in `hw4d/shot-0008.png`). (3) QEMU TCG here is single-threaded (`info cpus`: one `thread_id` for all vCPUs), so `-smp 4` is much slower than `-smp 1` for the same boot. (4) A worktree-isolated agent shell refuses `source` and some compound commands: keep helper scripts as files.
- **Lesson:** when a guest hangs under the layer, run the same QEMU command with no layer first (`ctl.sh` style control): here it showed in one run that the layer was innocent for the INTx storm and guilty for the 0xA0.
- **Review fixes (2026-10-21), all host-tested.** (1) LPI queue: duplicates of an LPI id are now idempotent per state (at most one in-flight + one pending entry per id; a storming device can no longer fill the 64 slots; requeue merges into an existing pending copy). (2) `wel2_vcif.owner[]` is `int32_t`: with `int16_t` a vINTID >= 32768 (IDbits 16 advertised) became negative = "free LR" and stayed in flight for ever. (3) `GICR_PROPBASER/PENDBASER` writes while the model's `EnableLPIs` = 1 are UNPREDICTABLE in the architecture: ignored and not forwarded; the property table is only read (priority, enable bit 0) when the guest enabled LPIs and set PROPBASER, a disabled LPI is just EOI'd, default priority 0xa0 otherwise. (4) Physical INTIDs 1024..8191 are logged and ignored (they used to enter the SPI path).
- **Open point (CPU_OFF/CPU_ON divergence).** `vgic_vcpu_reset` clears the model's `EnableLPIs` and bases, but the physical `GICR_CTLR.EnableLPIs` cannot be cleared by software once set (it is only cleared by reset). After a guest `CPU_OFF`/`CPU_ON` of a core the physical redistributor may still have LPIs enabled with the old tables while the model says disabled; the layer then reads no table (default priority), but the physical state is stale. Not seen in the runs (Windows does not offline cores at boot). **[hypothesis, untested]**

## F-24 · M2 soak test (#63): no layer failure, three tooling traps (2026-10-21)
Context: `run-m2.sh` + `m2-login.sh`, login as the throwaway test account of `tools/autounattend`, 32 min idle at the desktop with light activity, `CPUIF=trap` and `CPUIF=hw`, QEMU TCG `-smp 4 -m 4G`. Result: **both modes stay up, no bugcheck, no UNEXPECTED/FATAL/unhandled/stray line, no LPI queue drop** in either serial log (details in `el2/boot/README.md`, "Soak test"). The problems found were all in the test tooling:
- **`sendkey spc` to dismiss the lock screen can land in the password field.** The login failed ("Password non corretta", the field held 7 characters). `m2-login.sh login` now sends a `backspace` after the space (harmless if the space was consumed by the lock screen). **[verified: second login in both modes went through in one go]**
- **Wake key.** `sendkey ctrl` every `SHOT_EVERY` seconds replaces `sendkey shift` (no Sticky Keys dialog seen in either run; Ctrl alone triggers nothing in Windows or at the lock screen). **[verified: screenshots]**
- **First logon is slow.** After the password, "Ti diamo il benvenuto" (profile creation) takes about 3 minutes under TCG with 4 cores before the desktop appears; during it the trapped IAR rate is 5-10 times the later idle rate. Rates measured in the first ~30 minutes after the first logon are therefore not idle rates.
- Not a failure but a measurement caveat: rates are computed per guest second (`CNTVCT/CNTFRQ`), and TCG guest time does not advance at the host's wall-clock speed (about 1:1 to 1.3:1 here).

## F-25 · M2.x-1: GICv2m MSIs lost because the layer left the physical SPI level-sensitive (2026-10-21) - SOLVED
Context: `run-m2.sh MSI=gicv2m` (QEMU `-M virt,virtualization=on,gic-version=3,its=off,msi=gicv2m`), Windows disk `snapshot=on`.
- **Symptom:** with the layer, Windows boots, enables the NVMe interrupts and restarts at 177 s with `INACCESSIBLE_BOOT_DEVICE (0x7B)` (Automatic Repair on the next boot). The same machine without the layer (`NOLAYER=1`) reaches the lock screen in 6-7 min. **[verified: `v2m-hw-t2` vs `v2m-ctl`]**
- **Cause [verified: GICD trace]:** Windows sets `GICD_ICFGR` of INTID 80-84 (the v2m frame range) to edge before enabling them. The layer kept the guest's ICFGR only in the model and left the physical SPIs level; QEMU's v2m delivers an MSI as a pulse of the SPI line, which is lost on a level-configured SPI, so no completion ever reached the guest. (Design note, `watari-el2-devirq` ARCHITECTURE section 4: "ICFGR is not forwarded".)
- **Fix:** `VGIC_EFFECT_SET_TRIGGER` emitted by the vGIC on an SPI ICFGR change; `cpuif_vgic_effect` records the edge bit and calls `gic_phys_spi_trigger` (physical ICFGR written with the SPI disabled); the physical SPI handler latches an edge SPI as pending (line up then down) and does not mask it at the GICD or unmask it at EOI. Host tests added. One fix round. **[verified: desktop reached in hw and trap mode]**
- **`msi=off`:** with and without the layer Windows stays on the TianoCore logo for 600 s. Same as F-23 (`its=off`): the MADT of `its=off` has no MSI frame either (Q-D1), so this is the "no MSI controller" case. The INTx storm of F-23 was not seen in the per-core injection counters of `off-hw` at 600 s (injections about equal to timer ticks); the hang itself is reproduced. #65 stays open as "INTx on this QEMU does not work for Windows", not as a layer bug.
- **Tooling traps:** (1) the QEMU monitor `pmemsave` needs the file name in double quotes, otherwise `/` is parsed as a division (`invalid char 't' in expression`); (2) `m2-login.sh login` after a manual space leaves two characters in the password field (wrong password): only send `login`.

## F-26 · Hardening follow-ups #60/#64: two model errors and one test trap (2026-10-21)
- **`PRIbits` of 8 does not exist.** `vcif_init` accepted `ICH_VTR_EL2.PRIbits+1` up to 8; IHI 0069H.b 12.4.9 allows 5..7 (`0b100..0b110`), and `PREbits+1` must not exceed `PRIbits+1`. Corrected (clamps and tests); no hardware ever reported 8, so nothing had failed. **[verified: spec text]**
- **The vGIC model stores only 5 priority bits (`PRIO_MASK 0xF8`).** A host test of PREbits 6/7 that wrote priority `0xfe` through `GICR_IPRIORITYR` read `0xf8` back, so the first expectations (AP1R3 bit 30) were wrong. Not a bug (the guest-visible granule is 8), but the wider AP registers are exercised through LRs filled by hand (`t_fine_lr_priorities`); the guest cannot reach the upper PREbits through the model yet.
- **A "quiet" flag in the payload must be per core.** The cross-core kick test first silenced the virtual timer with one global flag read by the shared IRQ handler; cores 2 and 3 then stopped re-arming their timers too, and core 2 never saw `g_go_off` (WFI wake-up lost): `cpu 2 DID NOT GO OFF` in `run-m1-3.sh`, deterministic, and nothing to do with the kick. The flag is now checked as `g_xc_quiet && cpu == 1`.
- **`ICC_HPPIR1_EL1` ignoring PMR (the hypothesis of F-22) is what the spec says**: HPPIR has no "of sufficient priority" qualifier, IAR has. No code change. **[verified: IHI 0069H.b 12.2.10 vs 12.2.12]**
- **Mutation check of the kick test.** With the old rule (kick only a core that has a free LR) `run-m1-3.sh` delivers the better SGI as the second interrupt (3, 11, 4, 5, 6) and reports the eviction test as FAILED; with the predicate it is first (11, 3, 4, 5, 6). **[verified]**
- **Limits.** QEMU's `ICH_VTR_EL2` has PRIbits = PREbits = 5, so widths 6 and 7 are host-test only. The page-table cache maintenance and the E2H = 1 layout (F-22) still need the real M1.
