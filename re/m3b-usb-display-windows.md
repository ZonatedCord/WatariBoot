## 1. USB: the hand-over state, restated with the new facts

From `re/m3b-inherited-state.md` 4.2 (all [verified] there): m1n1 powers the PMGR domains of `atc-phy<N>`, `dart-usb<N>`, `usb-drd<N>`, programs the PHY for a "dummy" PIPE (USB2 only), runs DWC3 in **device mode** for the proxy console, and at the tail of `m1n1_main` stops and soft-resets the DWC3 and does not power anything down.

New, read for this task:
- The shutdown of each DWC3 also tears down its DART use: it unmaps four buffers (TRB ring, transfer buffer, scratchpad, event buffer) and then calls `dart_shutdown`, which, if the DART is neither locked nor `keep_pts`, writes the stream's TCR to `tcr_disabled` = `BYPASS_DAPF | BYPASS_DART` and zeroes the TTBRs [verified: m1n1 src/usb_dwc3.c:1294-1297, 1312-1313; src/dart.c:154, 733-736; src/usb.c:84 (`usb_dart_init` passes keep_pts = false), 450-461 (loops over every registered USB iodev)]. Consequence: the stream m1n1 used is left in **hardware bypass, translate off** [verified by reading the code, not measured]; the other stream of the controller and the other controller's DART are untouched [hypothesis]. If dart-usb is **locked** (CONFIG bit 15) the TCR write is skipped and translation stays on with empty tables; the lock bit read on hardware (ehw2) settles it.
- This also kills the idea of doing the host-mode bring-up from the host Mac's Python **through the proxy** and then handing over: the tail of `m1n1_main` runs after `kboot_boot` and would undo it (soft reset, DART TCR rewrite). The bring-up has to happen **after** the hand-over [hypothesis: only if the loader keeps calling `kboot_boot`; a loader that skips the tail was not examined].

## 2. USB: what has to happen, from the drivers that do it

### 2.1 The Apple DWC3 glue (Apple-specific order)
The asahi DWC3 glue documents the platform's required order in its header comment [verified: asahi `drivers/usb/dwc3/dwc3-apple.c:20-69`]:
1. The PHY is brought up first, for a known mode (USB3, USB3+DP, USB4) and lane orientation (through the Type-C mux call).
2. DWC3 is brought up, but the gadget area is not touched and xHCI is not started.
3. The PHY bring-up is finalised and DWC3's PIPE interface is switched from the dummy to the USB3 PHY (`phy_set_mode`).
4. Only now xHCI or the gadget is initialised.
Getting the order wrong gives a port that is dead until a PHY+DWC3 reset, or until a full SoC reset, or "some watchdog kicks in after a few seconds and forces a full SoC reset (mostly seen with USB4/Thunderbolt)" [verified: same file :51-55]. That last point is a **hazard for experiments**: a wrong USB-C step can reset the machine (recoverable, but it ends the session).

More facts from the same file:
- The USB2 PHY must be set to host (or device) mode **while it is still powered off**, before DWC3 touches it; the USB3 PHY is configured later, after DWC3 core init [verified: dwc3-apple.c:223-240, 267-272].
- A reset line (owned by the PHY, `resets = <&atcphy0>`) is deasserted before core init and asserted again on teardown [verified: dwc3-apple.c:246-254, 308-310; DT `dwc3_0` node, asahi `t8103.dtsi` ~1647-1675].
- SUSPHY must be enabled early "to properly configure the PHY and switch dwc3's PIPE interface to USB3 PHY" [verified: dwc3-apple.c:267-272].
- Vendor registers at +0xcd00..0xcdff of the controller ("identified by tracing XNU's memory access patterns"): three values are written after core init (LFPS offset 0x0f800f80 at 0xcd38, BW_NGT 0x0fc00fc0 at 0xcd3c, three timers at 0xcd40) [verified: dwc3-apple.c:113-128, 131-156, 255-262]. "Without these USB3 devices sometimes don't work" [verified: :109-111]. Whether USB2 needs them: **[hypothesis: no]**.
- Hot-plug: after PHY and DWC3 are initialised "we will only ever see a single new device connected event"; the PD chip resets the stateful eUSB2 repeater out-of-band on every CC (dis)connect, which needs a PHY reset. Apple's driver therefore tears everything down on every cable event and defers the first DWC3 probe until the first cable event [verified: dwc3-apple.c:41-69]. **For Windows this means: devices attached before boot only**; a cable event after the xHCI started will silently kill the port (no PD driver in the guest to redo the sequence). No interrupt arrives in that state, so Windows would not even notice [verified: :42-45].

### 2.2 The ATC PHY
- "No documentation for this PHY is available"; the driver was reverse engineered by watching XNU through a thin hypervisor. "In order to correctly setup the high speed lanes for the various modes calibration values copied from Apple's firmware by our bootloader m1n1 are required. Without these only USB2 operation is possible" [verified: asahi `drivers/phy/apple/atc.c:12-19`].
- Resources per PHY: `core` 0x383000000 (0x4c000), `lpdptx` 0x383050000, `axi2af` 0x380000000, `usb2phy` 0x382a90000, `pipehandler` 0x382a84000 for ATC0; the +0x2_0000_0000 twins (0x503000000 etc.) for ATC1 [verified: asahi `t8103.dtsi` atcphy0 and atcphy1 nodes]. The PHY is also the reset controller of its DWC3 (`#reset-cells = <0>`) [verified: same node, atc.c:9-10].
- Tunables, nine groups: `axi2af`, `common-a`, `common-b`, `lane0/1-usb`, `lane0/1-cio`, `lane0/1-dp` [verified: atc.c:2397-2405]. m1n1 builds them from ADT `tunable_*` properties of the `atc-phy<N>` node: for t8103 e.g. `tunable_ATC0AXI2AF`, `tunable_ATC_FABRIC` (+0x45000), `tunable_USB_ACIOPHY_TOP`, `tunable_AUS_CMN_*`, `tunable_AUSPLL_*`, `tunable_CIO3PLL_*`, `tunable_USB_LN0/LN1_AUSPMA_{TX_TOP,RX_TOP,RX_SHM,RX_EQ}` [verified: m1n1 src/kboot_atc.c:72-100]. So **the ADT in RAM already contains everything the layer or EDK2 would need**, as (offset, mask, value) triples; applying them is a masked write loop [hypothesis for the loop shape; Linux `apple_tunable_apply` not read].
- Power-up registers: `ATCPHY_POWER_CTRL` 0x20000 with SLEEP_SMALL/SLEEP_BIG/CLAMP_EN/APB_RESET_N/PHY_RESET_N bits; lane mode and crossbar protocol registers (`ACIOPHY_CROSSBAR_PROTOCOL_USB3` 0xa, swapped 0xb; lane mode USB3 = 1 at 0x48 on t8103); `MISC_LANE_SWAP` bit 2 for the cable orientation [verified: atc.c:150-168, 226-236].
- Pipehandler (the PIPE mux in front of DWC3): states DUMMY (USB2 only), USB3, USB4; `MUX_CTRL` data field 0 = USB3, 2 = DUMMY and clock field 1 = USB3, 4 = DUMMY; `LOCK_REQ/ACK` handshake; `AON_GEN` bit 0 = DWC3 reset_n; `NONSELECTED_OVERRIDE` [verified: atc.c:460-495, 533-548]. m1n1's `usb_init` writes the DUMMY values (`MUX_CTRL = 0x22`, `AON_GEN = DWC3_RESET_N`, `NONSELECTED_OVERRIDE = 0x9332`) [verified: `re/m3b-inherited-state.md` 4.2, itself citing m1n1 src/usb.c:126-160, 318-351; 0x22 = clock DUMMY(4)<<3 | data DUMMY(2), consistent with atc.c:471-480].
- **USB2-only host is the cheap case.** The DUMMY state is exactly what m1n1 leaves; the USB2 PHY path (`usb2phy` block, `USB2PHY_SIG_HOST` bits 14:12 = 7, `USBCTL` mode) is a handful of registers [verified: atc.c:497-516]. Supporting evidence that a firmware stage runs USB2 host on m1n1's PHY set-up with almost no PHY code: U-Boot's `drivers/phy/phy-apple-atc.c` is a 55-line stub (PHY ops empty, reset `of_xlate` only), U-Boot's `xhci-dwc3` driver matches `apple,t8103-dwc3`, and the Asahi docs state that U-Boot "provides ... support for booting from USB" and the U-Boot board page lists "USB 3.1 Type-C ports" as supported [verified: uboot drivers/phy/phy-apple-atc.c (55 lines), drivers/usb/host/xhci-dwc3.c:244-248; docs `docs/platform/open-os-interop.md:93,105`; https://docs.u-boot-project.org/en/latest/board/apple/m1.html]. That U-Boot's USB works at USB2 speed only, and with m1n1's help only, is **[hypothesis: inferred from the stub; not stated anywhere]**.
- Linux status: the Asahi feature matrix lists "USB2 (TB ports)" and "USB3 (TB ports)" as 7.0 for M1, "USB-PD" 5.16, Thunderbolt WIP [verified: docs `docs/platform/feature-support/m1.md:28-30, 49`]. j293 has only Thunderbolt/USB4-class ports (two USB-C on the left side, `typec0` back and `typec1` front) [verified: asahi `t8103-j293.dts:66-75`].

### 2.3 The PD controller (CD3217 "ACE2", tipd)
- On t8103 the ports have one CD3217 each on i2c0 (`hpm0` 0x38, `hpm1` 0x3f), compatible `apple,cd321x` [verified: `re/m3b-inherited-state.md` 4.2; uboot DTS nodes `apple,cd321x` e.g. t8103-j456.dts, seen by code search]. The chip is "probably actual new silicon" related to a TPS6598x [verified: docs `docs/hw/soc/usb-pd.md` (chips list)].
- Linux's `tipd` driver (mainline v6.12 has CD321x support) switches the chip to power state S0, unmasks its three interrupts (power status, data status, plug event) -- they are all **masked initially** -- and on events sets the cable orientation and the USB role (host/device/none) through role-switch and typec calls [verified: linux `drivers/usb/typec/tipd/core.c:1336-1345` (init), 255-265 (role), 295-321 (orientation), 529-560 (`cd321x_interrupt`)]. The orientation goes to the PHY (lane swap), the role to the DWC3 glue.
- Mac-side effect of m1n1: the interrupt masks are left **disabled** on the kboot path [verified: `re/m3b-inherited-state.md` 4.2 and risk 4].
- Can the firmware skip tipd? The tipd driver exists to get orientation, role and power events. A fixed-orientation USB2-only configuration might work with the plug in one orientation only, and role may default correctly if a device (not a host) is attached **[hypothesis; nothing public says what the chip does by default for data role]**. Whether the Mac sources 5 V on the port without the AP configuring anything is also **[hypothesis, needs hardware]**. A read-only look at the chip's status registers from EDK2 would settle part of it; I2C is a transaction, not a pure register read, so Marco should approve it as an experiment step.

### 2.4 DWC3 as an xHCI host
- DWC3 exposes the xHCI register set in the first part of its window; Linux treats `0x0..0x7fff` as the xHCI range and the DWC3 global registers start at `0xc100` [verified: linux `drivers/usb/dwc3/core.h:85-87` (`DWC3_XHCI_REGS_START 0x0`, `_END 0x7fff`, `DWC3_GLOBALS_REGS_START 0xc100`); `host.c:39-40` ioremaps `DWC3_XHCI_REGS_END` to read `CAPLENGTH`/`HCSPARAMS1`]. `GCTL` (PRTCAPDIR) is at 0xc110, `GSNPSID` 0xc120 [verified: core.h:105, and re/m3b-inherited-state.md 5.4].
- ADT/DT window: `usb@382280000`, `reg = <0x382280000 0xcd00>` (core) and `<0x38228cd00 0x3200>` (Apple vendor block); one level interrupt AIC 777 (usb-drd0) and 857 (usb-drd1) [verified: asahi `t8103.dtsi` dwc3_0/dwc3_1 nodes; `re/m3a-ehw0-measurements.md` Row 11].
- Standard xHCI compliance of the Synopsys core is the normal case (it is the xHCI host used on many SoCs); Linux applies no Apple-specific xHCI quirk beyond the generic DWC3 `plat_start` hook [verified: linux host.c:63-79 (the only quirk struct); nothing Apple in the t8103 node: no `snps,*` quirk properties in the `dwc3_0` node]. Microsoft says its xHCI driver targets "xHCI spec compliant" hardware and that a vendor needs its own UCX-based driver for non-compliant hardware [verified: https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/developing-windows-drivers-for-usb-host-controllers]. Whether USBXHCI accepts this core without a filter or a registry quirk: **[hypothesis: yes for a compliant core; to be proven on hardware, nothing on the bench can say]**.
- DMA coherency: the `dwc3_0` DT node has no `dma-coherent` property, so Linux treats it as non-coherent [verified: asahi `t8103.dtsi` dwc3_0 node as read]. Windows ARM64 needs `_CCA` in the DSDT to be told [hypothesis: ACPI `_CCA 0` = non-coherent; how the inbox xHCI driver behaves on a non-coherent controller, with common buffers, is **not documented anywhere I found**]. This is the single biggest unknown on the Windows side (open question Q-U3). EDK2 has a mechanism for non-coherent platform xHCI (`NON_DISCOVERABLE_DEVICE` with `DmaType` Coherent/NonCoherent, `NonDiscoverablePciDeviceDxe` with an xHCI device GUID, and `XhciDxe` on top) [verified: edk2 `MdeModulePkg/Include/Protocol/NonDiscoverableDevice.h:26-27,55-57`; `NonDiscoverablePciDeviceDxe.c:25,31` (EHCI and XHCI GUIDs); both on `master`, tag not pinned], which also gives EDK2 a keyboard path (R-E14) from the same bring-up.

## 3. USB: the DART question

Facts:
- t8103 DART (`DART_T8020` family): 16 streams, **32-bit input (IAS), 36-bit output (OAS)**, 4 TTBRs per stream [verified: linux `drivers/iommu/apple-dart.c:1125-1127, 1200-1219`]. Page size is read from `PARAMS1` bits 27:24; "bypass supported" from `PARAMS2` bit 0 [verified: apple-dart.c:44, 47, 1119-1120]. U-Boot's driver hard-codes 16 KB for the DART page [verified: uboot `drivers/iommu/apple_dart.c:62` `DART_PAGE_SIZE SZ_16K`], which upgrades the 16 KB figure of `re/m3b-ans-windows.md` 1.5 from hypothesis to "two independent drivers assume it" (hardware read still pending).
- Bypass is two TCR bits per stream: `BYPASS_DART` (bit 8) and `BYPASS_DAPF` (bit 12); translate enable is bit 7 [verified: apple-dart.c:80-81; m1n1 src/dart.c:44-46, 154 (m1n1's own "disabled" state is exactly the two bypass bits)]. The config **lock bit** (CONFIG bit 15) prevents changes; m1n1 sets it only for dart-disp0 [verified: m1n1 src/dart.c:15, 344-364; `re/m3b-inherited-state.md` 1.2 for kboot.c:1935]. dart-usb is therefore presumably **unlocked** [hypothesis: m1n1 programs it itself and never locks it; the lock bit is readable, ehw2 5.3 reads it. If it is locked, the shutdown write of section 1 is skipped].
- Linux uses the identity (hardware bypass) domain **by default whenever the DART page is larger than the CPU page** [verified: apple-dart.c:942-949 `apple_dart_def_domain_type`]. So a 4 KB-page kernel on a 16 KB-page DART runs its devices through bypass: a precedent for "bypass is a working configuration on the M1", but I found no statement that it was exercised on t8103 hardware: real DMA through that path happens only on 4 KB-page kernels, which are not the common Asahi configuration [hypothesis]. U-Boot's DART driver also has a `priv->bypass` mode that returns the address unchanged (`drivers/iommu/apple_dart.c:122`), another sign that bypass is meant to be identity, still not proof of 36-bit width [verified: code read].
- Each DWC3 sits behind **two** DARTs: `dwc3_0_dart_0` (stream 0) and `dwc3_0_dart_1` (stream 1), both on the ATC0 power domain, sharing IRQ 781 [verified: asahi `t8103.dtsi` dwc3_0 `iommus` and the two iommu nodes; the DARTs are at 0x382f00000 and 0x382f80000; ATC1: 0x502f00000, 0x502f80000, IRQ 861]. Both streams need handling.

Not known (decisive for xHCI):
- Does bypass emit the **full 36-bit physical address**, or is it limited by the 32-bit input address? The controller will be given physical addresses 0x8_0xxx_xxxx by Windows. If bypass only passes 32-bit IOVAs, Windows' addresses cannot work and a translation with the layer-built page tables (IOVA < 4 GB mapped to guest RAM above 32 GB, with Windows' 4 KB pages needing 16 KB DART granules) would be unavoidable **[hypothesis: not found in any source read]**.
- Whether a dart-usb entry survives or must be rebuilt after the layer's stage-2 is active: the DART is a DMA path, **not** subject to the CPU's stage 2; so the controller (once started by a guest driver) could write anywhere its DART allows, including the layer's memory. With bypass the guest owns all RAM by DMA; only a layer-built translation would give isolation. This is acceptable for the single-OS first boot (design says the layer is not a security boundary against the guest [hypothesis: stated here as the assumption], and Windows gets the whole disk anyway) but must be recorded.

The layer-side options: (i) set both bypass bits for the two streams of the used controller once, before the first `eret` (a handful of register writes, plus checking the lock bit first); (ii) program real translation (a page-table builder for 16 KB DART granules mapping the guest RAM window; large, and the guest's addresses would be IOVAs that Windows does not know: needs an IORT description, section 4). Recommendation: (i), and measure whether it works (step H3 in section 8).

## 4. USB: what Windows sees

- **ACPI node.** Microsoft: on SoC platforms the USB host controller can be enumerated by ACPI; the namespace carries a vendor `_HID`, a `_UID` if there is more than one, a `_CID` of `PNP0D10` for xHCI, and `_CRS` with the resources; Windows includes inbox drivers for EHCI/XHCI-compliant controllers [verified: https://learn.microsoft.com/en-us/windows-hardware/drivers/bringup/other-acpi-namespace-objects, "USB host controllers and devices"]. `PNP0D10` = "XHCI-compliant USB controller with standard debug", `PNP0D15` = without standard debug; Windows prefers `_HID` over `_CID` matching [verified: https://learn.microsoft.com/en-us/windows-hardware/drivers/bringup/device-management-namespace-objects; DESIGN 9.2]. For a first test `_CID` `PNP0D15` (no standard debug capability) is the more honest ID **[hypothesis: the DWC3 may not implement the xHCI debug capability; the xHCI extended capability list would say]**.
- **Resources for `_CRS`.** One memory range `0x382280000`, length 0x8000 (the xHCI part only), and one interrupt: GSIV 809 (AIC 777 -> vINTID 809), level, active high [verified: R:`docs/design/watari-el2-devirq/ARCHITECTURE.md:13, 228, 234`; the length 0x8000 vs the 0xcd00 of that table: see 6]. The address is above 4 GB, so the descriptor must be a 64-bit memory descriptor (`QWordMemory` style) rather than `Memory32Fixed` **[hypothesis: ACPI resource-template detail, not re-read]**. Add `_CCA` (Q-U3), `_UID`, and for ports `_UPC`/`_PLD` and a root-hub child with `_ADR 0` (Microsoft's hierarchy rules) [verified: MS other-acpi-namespace-objects, same page, "USB port-specific objects" and the `_ADR` hierarchy section].
- **IOMMU description.** Windows learns IOMMU stream mappings for ACPI devices on ARM64 from the IORT (`IOMMU_DEVICE_CREATION_CONFIGURATION_ACPI` "is required for ACPI devices on ARM64 systems") [verified: `re/m3b-ans-windows.md` 2.3, URL there]. If the DART is **not** in the IORT, Windows treats DMA addresses as physical, which is the intended bypass design [hypothesis; untested].
- **Interrupt handling at hand-off.** Microsoft requires interrupts of OS-managed devices to be masked at ExitBootServices until the driver enables them [verified: https://learn.microsoft.com/en-us/windows-hardware/drivers/bringup/uefi-requirements-that-apply-to-all-windows-platforms, "Platform setup requirements: Core system resources"]. If EDK2 started the xHCI for a keyboard it must halt and reset it at ExitBootServices Tension to resolve: Microsoft wants one debug-capable controller "powered, clocked and initialized by the firmware before OS handoff" (next bullet), while the interrupt rule above means any xHCI EDK2 used must be quiet at ExitBootServices; halting and resetting it at that point also drops the initialised state the debug requirement asks for. Resolution: reset it to a clean halted, powered, clocked state and let Windows re-initialise it **[hypothesis; whether that satisfies the debug rule is untested]** (EDK2's `XhciDxe` does a halt+reset in its start path; not read for the exit-boot-services event [hypothesis]). The layer's guard masks the DART IRQ 781 so an unexpected DART fault is a counted guard trip rather than a storm [verified: devirq ARCHITECTURE.md:228].
- **Debugging requirement.** Microsoft asks for one debug-capable port (xHCI/EHCI/serial/...) powered and initialised before hand-off [verified: same UEFI page, "Debugging"; DESIGN 7 says our first platform does not meet it]. A working xHCI with `PNP0D10`, an exposed Type-C port and the standard debug capability would fix this requirement as a side effect **[hypothesis: only if the core implements the debug capability]**.
- **Power management.** No PMGR domain, PHY or DART is exposed to the guest (inherited-state risk 6); no `_PS0/_PS3` methods, so Windows sees the device as always on. Sleep/D3cold of the xHCI is out of scope [verified: D3cold is an opt-in described in the same Microsoft page; absence of methods is our choice].

## 5. USB: where the bring-up code can live (decision for Marco)

The sequence of 2.1 needs: I2C to the PD chip, the ATC PHY (tunables from the ADT, orientation), DWC3 core init in host mode with the Apple writes, DART bypass, and PMGR domains already on. Options:

| | Where | Needs from the layer | Size [hypothesis] | Fits "minimal layer"? |
|---|---|---|---|---|
| A | Host Mac's Python over the proxy, before the hand-over | nothing | none in firmware | **Not viable alone**: m1n1's tail soft-resets DWC3 and rewrites the DART stream afterwards (section 1) |

Marco must approve |
| C | EDK2 DXE driver at EL1 (the NTASP tree has `AppleUsbTypeCBringupDxe` and `AppleDartIoMmuDxe` as reference only, ADR-0007) [verified: DESIGN section 2 table, citing `gh api` tree] | stage-2 windows for PHY, pipehandler, DART, I2C0 in the guest, from the layer's FDT; the ADT tunables handed over in the guest FDT | same as B but in the guest | **Stretches** "guest sees only RAM, vGIC, timer, framebuffer" (DESIGN 4.2, 5) and hands DMA-master control to the guest; smaller blast radius than B (the layer stays small) |

B should be chosen only if Marco prefers not to expose PHY/DART/I2C to the guest at all. **Either choice is a scope extension and needs Marco's explicit approval.**

## 7. Display

### 7.1 What Windows' BasicDisplay does with a GOP framebuffer
- **Microsoft's firmware rules**, restated from DESIGN 8.1 and re-read today: GOP required; native resolution; `PixelsPerScanLine` = `HorizontalResolution`; `PixelFormat` = `PixelBlueGreenRedReserved8BitPerColor`; a physical framebuffer (`PixelBltOnly` not supported); firmware must not touch the framebuffer once a boot application runs; it must stay scanned out after boot services exit [verified: MS-UEFI, https://learn.microsoft.com/en-us/windows-hardware/drivers/bringup/uefi-requirements-that-apply-to-all-windows-platforms, "Protocol requirements"]. GOP is listed as a *conditionally required* protocol and an *explicit Windows requirement* [verified: same page, summary table]. The wording is a MUST: `PixelsPerScanLine` must equal `HorizontalResolution`, `PixelFormat` must be `PixelBlueGreenRedReserved8BitPerColor`, a physical frame buffer is required and `PixelBltOnly` is not supported.
- **The driver:** "BasicDisplay's primary purpose is to enable Windows to write to the display controller's linear frame buffer"; "On UEFI platforms, BasicDisplay inherits the linear frame buffer that is set during boot. In this case, no mode or resolution changes are possible"; it supports UEFI GOP [verified: https://learn.microsoft.com/en-us/windows-hardware/drivers/display/microsoft-basic-display-driver]. Basic Display is always used together with BasicRender (WARP) [verified: same page].
- **The public sample of the same model (KMDOD).** Display-only drivers "can only return display modes of D3DDDIFMT_A8R8G8B8"; the pixel format helper knows P8, R5G6B5, R8G8B8, X8R8G8B8, A8R8G8B8 and asserts "unknown" for anything else (so no A2R10G10B10) [verified: KMDOD `bdd_dmm.cxx:11-16`, `bdd.hxx:322-334`]. The framebuffer comes from the system: "This sample driver only uses the frame buffer of the POST device. DxgkCbAcquirePostDisplayOwnership gives you the frame buffer address", with the physical address, pitch, size and colour format in `DispInfo` [verified: KMDOD `bdd.cxx:80-82, 567`]. It maps the physical range with `MmMapIoSpaceEx` as read/write **write-combined**, falling back to non-cached [verified: KMDOD `bdd_util.cxx:66-76`]. That the inbox BasicDisplay behaves like the sample is **[hypothesis]**; the sample is the documented basis of the model.
- **How Windows finds the framebuffer** from the firmware: through GOP's `Mode` information captured by the boot loader before ExitBootServices and passed on [hypothesis: no Microsoft page describes the hand-over inside the loader; consistent with the sentence "inherits the linear frame buffer that is set during boot"]. No ACPI display device is needed for BasicDisplay [hypothesis]; the ACPI `_BCL/_BCM` brightness methods are required only "if the embedded LCD supports brightness control" [verified: MS other-acpi-namespace-objects, display table], which we cannot offer (SMC/DCP own brightness: inherited-state 2.2). BGRT is the boot-logo table and not a framebuffer carrier [hypothesis; the Microsoft "boot screen components" page was found but not read].
- **Resolution and stride.** 2560 x 1600 is the native panel [verified: ehw0, DESIGN 8.1]; stride = width x 4 = 10240 because m1n1 sets `stride = width * 4` in its own swap [verified: m1n1 src/display.c:523, 563, 575-582], which matches Microsoft's "PixelsPerScanLine = HorizontalResolution" rule. No limit on size was found in the sources; the buffer is 16 384 000 bytes [verified: DESIGN 8.3 arithmetic].
- **Stage-2 memory type.** Windows maps write-combined (Normal-NC at stage 1) as above; the layer's stage-2 mapping is Normal-NC so that the combination stays Normal-NC [hypothesis: DESIGN 8.3 item 1, from the Arm ARM combination rules; the mapping itself is now implemented as Normal-NC (E9)]. The framebuffer above the RAM top must be described to Windows as MMIO by EDK2's GCD, since the layer does not list it in `/memory` [verified: DESIGN 5].

### 7.2 What 10-bit means for Windows
- The panel buffer is **x2r10g10b10, 30 bpp** [verified: m1n1 src/display.c:575-582 sets `depth = 30`; surface format `FMT_w30r` hard-coded in `display_swap`, src/display.c:381; DESIGN 8.1].
- Windows' documented path is 32-bit BGR8. For a `PixelBitMask` GOP with 10-bit masks I found **no Microsoft page, test description or sample that says it is accepted**; the public sample's format list excludes it (7.1). The legacy Microsoft GOP test (HCK) still states "PixelFormat must be PixelBlueGreenRedReserved8BitPerColor" [verified: web search result for "UEFI GOP mode Test", https://msdn.microsoft.com/en-us/library/windows/hardware/hh997769(v=vs.85); content seen only as a snippet, so treat as hypothesis for its exact wording]. Conclusion: option (a) contradicts the stated MUST; it works only if the Windows loader is lenient [hypothesis]; unproven either way.

### 7.3 Options for the 30-bit panel (DESIGN R-E1), re-ranked
| # | Option | Colour | Cost / risk | Approval |
|---|---|---|---|---|
| a | Truthful `PixelBitMask` x2r10g10b10 (as designed for EDK2's own GraphicsConsole) | exact for EDK2; Windows unknown | none | no |
