Items checked and found sound (evidence):

- **Secondary cores / PSCI (item 2).** First start: store, `dc cvac`, `dsb`, `sev` to the cpu-release-addr word, the reader runs MMU/caches off [verified: `cpu_start.c`, Linux `smp_spin_table.c` pattern as cited in `T6f-wiring.md`]. Day 2 L5 started all 7 secondaries (P cores = cluster 1, Aff1 = 1) on the real M1 and every core arrived [verified: `docs/sessions/2026-11-13-ciani-01.md`]. The layer implements `PSCI_VERSION`, `CPU_ON` (32/64), `CPU_OFF`, `AFFINITY_INFO`, `MIGRATE_INFO_TYPE`(2), `SYSTEM_OFF`, `SYSTEM_RESET`, `PSCI_FEATURES`; `CPU_SUSPEND` and `SYSTEM_RESET2` are NOT_SUPPORTED (H6). Not tested on hardware: `CPU_OFF` then `CPU_ON` of a parked core (park/wake path), `AFFINITY_INFO` under load, and seven `CPU_ON` calls in a few milliseconds from Windows (day 2's G9 starts the cores one after the other). CPU_OFF on the M1 cannot power a core down (no EL3, no PMGR use); it parks in the layer and `CPU_ON` wakes it with the flag + `sev`, restarting on a fresh stack (`secondary_rewake`) [verified: code]; a core can come back.
- **Interrupts (item 3).** Timers: the guest's virtual and physical timers raise FIQs gated by `VM_TMR_FIQ_ENA_EL2` bits 0/1; day 2 L4 (G7, G8) passed on hardware [verified: day-2 results]. IPIs: the sender writes `IPI_RR_GLOBAL_EL1` with core = Aff0 and cluster = Aff1 (Linux AIC uses MPIDR level 1 as cluster, Aff2 unused) [verified: `apple_fiq.c apple_ipi_value`]; G9/G10 passed on hardware. A kick to a core that is not yet started or is parked only leaves a pending masked FIQ; `apple_fiq_init_cpu` clears `IPI_SR` and the timer controls before the gates open (M-3) [verified: `apple_fiq.c`]. E and P cores use the same implementation registers here (`PMCR0_EL1`, `UPMCR0_EL1`, `VM_TMR_FIQ_ENA_EL2`, `IPI_*`); nothing in the layer branches on core type except the stack slot and the AIC core index (Aff0 + 4*Aff1), both measured on day 1 [verified: `re/m3a-ehw0-measurements.md` row 2]. The AIC is quiet on Monday: every source is masked and nothing is exposed to the guest (`pirq_aic_init`), and the guest has no devices (the DSDT lists only the eight CPUs), so Monday does not exercise the AIC IRQ path at all [verified: `pirq_aic.c:116-122`, `Dsdt.asl`]. The `CNTHCTL_EL2 = 0xf03` write is the E2H = 1 layout with EL1/EL0 counter and timer access open [verified: Arm ARM CNTHCTL_EL2, `cpuif.c:259` comment].
- **Watchdog (item 4).** m1n1 v1.6.1 `wdt_disable` clears `WDT_CTL` on the watchdogs at start-up and nothing in `kboot_boot` re-arms it [verified: `re/m3b-inherited-state.md` 1.2, m1n1 `src/wdt.c`]; the layer writes the watchdog only in `SYSTEM_RESET` and the `wel2.step=1` rung (`cpu_start.c wel2_cs_system_reset`), the page is mapped Device for EL2 and not mapped for the guest. Day 2 reset the machine twice in under 5 s from the layer. So the Mac cannot reset itself mid-boot **through this watchdog**; whether the SMC or iBoot keeps another liveness timer running while an unknown OS runs is unknown but Asahi Linux (no watchdog driver by default) runs for hours on the same stub [hypothesis, from Linux practice]. The longest hardware run so far is day 2's (minutes); day 3's hold (D3b) and day 4 add the first 10+ minute runs.
- **Cache coherency along the RAM-disk path (item 1).** (a) Loader to DRAM: the proxy `writemem` runs on core 0 with m1n1's cacheable map; the loader cleans every block to the PoC by VA (`dc cvau`, `dc cvac`, 32 MiB per request) and m1n1's tail runs `mmu_shutdown`, which cleans and invalidates the data cache by set/way on the boot core only [verified: DESIGN m1boot line 49, m1n1 `src/memory.c:636-643` as cited there]. The RAM disk's 713 MiB cannot all sit in the caches (a few MiB of L2), the rest reached DRAM by eviction; the explicit clean covers the tail. (b) Layer start: MMU/caches off; `start.S` invalidates (`dc ivac`) the whole layer block after relocating, `stage1.c clean_inval` cleans the page tables and shared globals by VA before the MMU turns on [verified: code]. The layer never reads the RAM disk. (c) Stage 2: the RAM-disk range is ordinary guest RAM (`wel2_s2_build_ram`, Normal WB inner-shareable, MemAttr 0b1111; `HCR_EL2.FWB` is kept 0 by a `_Static_assert`), the layer only cuts it out of the guest `/memory` and passes it in the FDT (`wel2_gfdt_place_ramdisk` refuses a range that is not wholly inside one guest RAM range). (d) EDK2: `AddMemorySpace` then `AllocatePages` then `SetMemoryAttributes(WB)`, then the CRC read through the new WB mapping [verified: `WatariM1RamDiskDxe.c`]: the CRC compare is the end-to-end proof that no stale or unflushed line sits between the loader and the guest, and a failure is logged and the disk is not registered, never silent. (e) Windows reads the same memory, cache-coherent across all cores. Guest-visible stage-2/stage-1 attribute combinations: S1 Device + S2 Normal = Device (MMU-off guest, intended); S1 WB + S2 WB = WB; S1 NC/WC + S2 NC (framebuffer) = NC. **Framebuffer:** at EL2 the panel is mapped Normal-NC (`MAIR` Attr2) at page granularity; it lies above RAM (0x9e2570000 vs RAM top 0x9df610000, about 50 MB apart) so no WB alias exists; the guest's part is stage-2 NC, `XN`, never cacheable; the layer's band part is unmapped for the guest [verified: `stage1.c`, `maps.c:354-372`, `main.c stage2_init`].
- **Guest stage 2 is RAM only on the M1** (`wel2_s2_build_ram`): the guest has no MMIO window except the trapped vGIC windows (`0xF_0000_0000`, `0xF_1000_0000`) and the MSI frame page. A guest access to anything else is a stage-2 translation fault at EL2, not an SError, and ends in `handle_dabt` "unhandled guest data abort" with the IPA printed [verified: `main.c:593-615`]. That is the right failure mode (the IPA is the diagnosis), and the j293 DSDT declares CPUs only, so Windows has nothing else to probe [verified: `Dsdt.asl`].
- **E2H = 1, 16 KB granule, DAIF (item 6).** E2H is stuck at 1 on the M1 (day 1) and the layer refuses to run without it; `enter_el1` writes the guest's `SCTLR_EL12`, the timers use the `_EL02` encodings, `s1_enable` reprograms E2H per core before `TCR_EL2`/`SCTLR_EL2` [verified: `start.S`, `stage1.c`]. The M1 supports 4 KB and 16 KB at stage 1 and stage 2 (`TGran4 = 0`, `TGran16 = 1`, `TGran4_2 = TGran16_2 = 2`), so a Windows 4 KB stage-1 under the layer's 16 KB stage 2 is legal (granules are independent per stage). DAIF is fully masked at EL2 on every entry (`reset`, `secondary_entry`, `secondary_rewake`); physical IRQ/FIQ/SError are routed to EL2 (IMO/FMO/AMO) so a guest's own PSTATE masks do not block them; an SError from the guest reaches the `fatal` path (vector 11), which is acceptable on Monday.

## Per-item detail

### H1: console spam on the IPI hot path (fixed)

`cpuif_sysreg_trap` (the `ICC_SGI1R_EL1`/`ASGI1R`/`SGI0R` write trap, both cpuif modes) called `put_kv` twice per trap with no budget and no `g_trace_on` check, while every other hot-path log in the layer is budgeted (`g_log_budget`, `g_eff_log_budget`, the 10x timer log, `g_hvc_log_budget`, the trace-gated lines). `el2_exception` takes the single big lock for every exception, and `puts_` mirrors every character to the S5L UART (poll budget 2^22 reads, then dropped after `WEL2_UART_MAX_FAILS`) and to the panel (band ticker: a full-width row fill on Normal-NC memory per line, then glyphs). The bench ran 414 896 IPIs in 3716 s (about 110 per second, about 850 000 log lines) and passed, but under TCG every instruction is slow and the panel is RAM; on the M1 the same lines cost a real UART poll, a 2560 x 20 pixel NC fill and the glyph stores, all with FIQs masked and every other core waiting for the lock. A Windows system with real load (DPC/IPI traffic, 8 cores) can send far more IPIs than an idle Setup page. Effect on Monday if left: a slow, stuttering Windows, possible `CLOCK_WATCHDOG_TIMEOUT` (0x101) or the 5-minute limits of the procedure missed for no real reason.
Fix (`el2/boot/cpuif.c`): `SGI_LOG_BUDGET = 32` lines logged, one notice line, then silent; `wel2.trace` keeps the full log; a counter `guest ICC_SGI*R writes trapped` is added to the final statistics. `run-m1-2.sh` expects only the first line, so the bench scripts are unaffected. `make -C el2 test` passes (includes the two `smc`/encoding checks and the host tests). The QEMU run-all was **not** run (another QEMU was running, 8 GB host): Opus runs `make -C el2/boot clean && el2/boot/run-all.sh` (46 PASS expected). **The hardware bundle must be rebuilt after this commit (day-4 gate WG-5).**

### H2: W1 with one vCPU

The j293 ACPI model lists eight CPUs. With `--no-smp` the layer's `/cpus` has one node (m1n1 removes the dead cores), so Windows' `CPU_ON` for cores 1-7 returns INVALID_PARAMETERS (`guest_cpu_from_target` finds no vCPU). On the bench, a MADT with more cores than vCPUs ended in `INTERNAL_POWER_ERROR (0xA0)` (T16b-2: 8 in the MADT, 4 vCPUs; the cause is [hypothesis], the parameters were not read). So for W1 the useful reading is: logo and spinner = S2/S3 reached; a bugcheck within about a minute after the logo = the expected consequence of one core, not a W1 failure. If Marco prefers one fewer unknown, W1c can already use `--smp` (day 3's D4 will have passed by then, WG-1 and R-W5), which is the configuration the bench validated end to end (T16d). Procedure note added.

### H3: all RAM above 4 GiB

The M1's RAM is at 0x8_0000_0000 (8 GB model: up to 0x9df610000). Bench RAM was at 0x4000_0000 (3-4 GiB), with the RAM disk at 0x8000_0000, so the bench never presented an environment without memory below 4 GiB. Known mechanisms to watch: (1) `psci.c cpu_on` with the SMC32 function ID masks the entry to 32 bits, and an entry in guest RAM above 4 GiB then fails `guest_ram_contains` (INVALID_ADDRESS); Windows ARM64 is expected to use the 64-bit `CPU_ON` (0xC4000003) [hypothesis, not verified; the bench log does not record the function id]; (2) EDK2 allocations limited to below 4 GiB (ACPI reclaim for FACS/DSDT fields, SMBIOS 32-bit tables) would fail with no RAM there; day 3's D3 reaches BDS with the production ACPI/SMBIOS installed, so it is the first evidence [hypothesis]; (3) Windows' own below-4 GiB needs (boot-time DMA buffers, `MmAllocateContiguousMemory` limits): not exposed on Monday, since no device exists. Cheap detector: the EDK2 ticker/`WatariM1AcpiDxe` lines on day 3 (ACPI installed, no allocation error), and the first winload screen on day 4.

### H4: memory the BLOCK CHECK cannot see

`check_blocks` proves each block lies in the FDT's usable list. It cannot see state outside the FDT: ANS2 (NVMe coprocessor, SART-listed buffers), DCP (display DART), PCIe root-port DARTs, SEP/SMC buffers. Day 1 showed m1n1 itself enabled the PMGR parents of ANS2; iBoot "puts some coprocessors to sleep" but which is unknown (`re/m3b-inherited-state.md` section 0 rows 4, 5, 15; section 3.3). If a running RTKit owns a buffer in RAM that the guest then uses, corruption is silent and late. Rung E (`ehw2`, read-only) reads `CPU_CONTROL` bit 4, the NVMe boot status word, the SART entries and the PMGR state to answer it. Recommendation: make rung E mandatory before W1 (5 minutes, read-only), and compare the SART entries with the guest RAM ranges of the D0 preview; Windows' 8 GB image is the first time lots of the usable RAM are written.

### H5: MMU-off guest and the EL2 cacheable alias

Arm ARM requires cache maintenance when the same location is accessed with mismatched attributes; the layer avoids the explicit cases (`dcache_clean_range` for the FDT, `hvc_clean_inv` for the entry header and HVC copies), and the EL2 core never *reads* guest RAM except those. What is not controlled is speculation/prefetch from the EL2 map (all guest RAM is Normal WB there). The standard hypervisor remedy is `HCR_EL2.DC = 1` while the guest MMU is off (guest Normal WB until its MMU is on) or a clean+invalidate of guest RAM when the guest turns its MMU on. Neither is applied; m1n1's hypervisor runs Linux-style guests on Apple CPUs without it [hypothesis: not re-read]. If day 3 shows EDK2 PrePi reading garbage right after its MMU turn-on, this is the first suspect; a `wel2.dc=1` boot argument (HCR_EL2.DC in `g_hcr` for guests that start MMU-off) would be the lever, to be added only after the failure is seen (needs a QEMU TCG regression run).
